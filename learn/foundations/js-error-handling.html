Custom Error Hierarchies, Stack Traces & Defensive Coding

هيكلة فئات الأخطاء المخصصة، تشريح الـ Stack Traces والبرمجة الدفاعية

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • بناء شجرة أخطاء مؤسسية مخصصة (Custom Error Hierarchy) ترث من فئة Error الأصلية.
  • فهم والتحكم في تسلسل تتبع الأخطاء باستخدام Error.captureStackTrace().
  • استخدام خاصية error.cause المضافة حديثاً لتتبع سلاسل أسباب الأخطاء المتسلسلة (Error Chaining).
  • التمييز الصارم بين الأخطاء التشغيلية المتوقعة (Operational Errors) وأخطاء المبرمجين البرمجية (Programmer Bugs).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في المشاريع المبتدئة، معالجة الأخطاء تقتصر على وضع console.log(error) داخل كتلة catch. النتيجة؟ عندما تحدث مشكلة في الإنتاج، يجد فريق الهندسة رسالة غامضة مثل Error: Something went wrong بدون أي تفاصيل عن هوية المستخدم، أو رقم الطلب، أو كود الخطأ الدقيق! في الأنظمة الإنتاجية الكبرى، معالجة الأخطاء هي "معمارية هندسية متكاملة" (Error Architecture). يجب أن يكون خادمك قادراً على التمييز التلقائي بين: 1. خطأ تشغيلي متوقع (Operational Error): مثل إدخال كلمة سر خاطئة أو انتهاء رصيد العميل (يجب معالجته وإرجاع كود 400 أو 402 برسالة واضحة للمستخدم). 2. خطأ برمجي كارثي (Programmer Bug): مثل محاولة قراءة خاصية من undefined أو فشل الاتصال بقاعدة البيانات (يجب تسجيله فوراً مع الـ Stack Trace وإرسال تنبيه لفريق On-Call). في هذا الدرس، هنتعلم إزاي نبني فئات أخطاء احترافية تدعم Error Causes والـ HTTP Status Codes، وإزاي ننظف الـ Stack Traces لحماية بيانات النظام الحساسة.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

بناء فئة الخطأ الأساسية (Base Custom Application Error)

إنشاء كلاس AppError يرث من Error ويحمل statusCode و isOperational و code لتصنيف المشاكل.

02

تنظيف الـ Stack Trace عبر Error.captureStackTrace

إزالة اسم مشيد كلاس الخطأ من الـ Stack Trace ليبدأ التسلسل مباشرة من السطر الحقيقي الذي تسبب في المشكلة.

03

ربط أسباب الأخطاء المتسلسلة (Error Chaining with error.cause)

استخدام new Error("High-level message", { cause: originalError }) لربط الخطأ الظاهري بالخطأ الجذري للـ Database.

04

المعالجة الدفاعية للمدخلات (Defensive Programming)

التحقق من صحة المعاملات عند مداخل الدوال (Guard Clauses) ورمي TypeError و RangeError فوراً قبل بدء المعالجة.

05

حراس الأخطاء العامة (Global Unhandled Rejection Guards)

إعداد مستمعي process.on("unhandledRejection") في Node.js أو window.addEventListener("unhandledrejection") في المتصفح.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

export class NotFoundError extends AppError {        // فئة خطأ مخصصة للموارد غير الموجودة
  constructor(resource = "Resource", id = "") {      // مشيد يقبل اسم المورد ومعرفه
    super(`${resource} with ID [${id}] not found.`, 404); // تمرير كود الحالة 404
    this.resource = resource;                        // بيانات وصفية إضافية للتحليل
  }                                                  // نهاية المشيد
}                                                    // نهاية الفئة

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ كارثي: صيد الخطأ وتجاهله بصمت (Silent Failure)
try {
  await chargeCreditCard(user, amount);
} catch (error) {
  // ترك الكتلة فارغة بدون تسجيل أو إعادة رمي!
}
✅ الحل الهندسي القياسي (Best Practice)
// الحل الهندسي: تسجيل وتصنيف الخطأ أو إعادة رميه
try {
  await chargeCreditCard(user, amount);
} catch (error) {
  logger.error("Payment processing failed", { userId: user.id, error });
  throw new PaymentError("Unable to process transaction", { cause: error });
}

التشخيص الهندسي: ابتلاع الأخطاء بصمت (Swallowing Errors) يخفي المشاكل الحرجة ويجعل تتبع الأعطال الأمنية والمالية في بيئات الإنتاج أمراً مستحيلاً.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: ما هي استراتيجيتك لمعالجة أخطاء الـ Unhandled Rejections والـ Uncaught Exceptions في خوادم Node.js الكبرى دون إيقاف الخدمة عن باقي المستخدمين؟

عند حدوث uncaughtException، يكون تطبيق Node.js في حالة غير مستقرة وغير مضمونة في الذاكرة (Corrupted State). الاستراتيجية السليمة هي: 1. تسجيل تفاصيل الخطأ في نظام المراقبة. 2. إيقاف استقبال اتصالات جديدة على الخادم. 3. إكمال الطلبات الجارية الحالية بحد أقصى (Graceful Shutdown مهلة 10 ثوانٍ). 4. إنهاء العملية بـ process.exit(1). 5. الاعتماد على مدير عمليات مثل PM2 أو Docker/Kubernetes لإعادة تشغيل الـ Container نظيفاً فوراً، مع توزيع الأحمال عبر Load Balancer لضمان عدم انقطاع الخدمة.
