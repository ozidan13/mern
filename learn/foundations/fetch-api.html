Fetch API, Streams & AbortController

سر مرحلتي الاستجابة، ولماذا لا تفشل دالة fetch عند أخطاء 404 أو 500؟

التقنيات: Fetch API · ReadableStream · AbortController · REST المستوى 2 30 دقيقة
أهداف الدرس ونقاط الإتقان · Learning Objectives
  • فهم لماذا يتطلب جلب البيانات مرحلتين: وصول الترويسات (Headers Arrival) ثم استهلاك التدفق (Body Stream Consumption).
  • استيعاب السلوك الصادم لدالة fetch مع رموز الخطأ وأهمية خاصية response.ok.
  • إلغاء الطلبات المعلقة وحماية الذاكرة ومنع تضارب الـ Race Conditions عبر AbortController.

1. القصة والتشبيه الواقعي · The Core Story

تشبيه استلام الطرد البريدي وفتح الصندوق · Parcel Receipt & Unboxing

تخيل إنك طلبت شاشة تلفزيون أونلاين.. أول ما مندوب الشحن يوصل عند باب البيت، بيمضي لك على إشعار الاستلام (Response Headers) ويقولك: "الطرد وصل بنجاح والحجم كذا".. دي المرحلة الأولى await fetch()!
لكن هل بمجرد ما المندوب وصل الشاشة بقت شغالة ومعروضة عندك في الصالة؟
طبعاً لأ! لسه محتاج تفتح الكرتونة وتفك السلوفان وتركب الكابلات خطوة بخطوة (Stream Consumption).. دي بقى المرحلة التانية await response.json()!
ولو غيرت رأيك والمندوب لسه في الطريق، بتستخدم زر الإلغاء الفوري (AbortController) عشان توقف الرحلة وتوفر فلوسك ووقتك!

الفخ الكبير الذي يقع فيه 90% من المطورين مع Fetch

دالة fetch() لا ترمي خطأ (Reject) إذا أرجع السيرفر كود 404 Not Found أو 500 Internal Server Error! الـ Promise بتعتبر الطلب ناجحاً طالما السيرفر رد عليك ولم تنقطع شبكة الإنترنت بالكامل. لذلك، كتابة if (!response.ok) هي خط الدفاع الإجباري الأول لأي مهندس محترف.

2. رحلة البيانات في مرحلتين · Step-by-Step Mechanics

1
1. استلام الترويسات (Header Resolution)

الـ Promise الأولى تنتهي فور استلام الـ HTTP Status و Headers، فنعرف فوراً نوع المحتوى Content-Type وحجمه دون انتظار تحميل كل البيانات.

2
2. فحص كود الحالة (Checking response.ok)

نتأكد أن كود الحالة يقع في النطاق السليم 200–299، فإذا كان 401 أو 404 نرمي استثناء يدوياً للـ Catch Block.

3
3. استهلاك التدفق الثنائي (Body Stream Parsing)

استدعاء response.json() أو response.text() يقرأ الـ ReadableStream بالكامل ويحوله لكائن جافاسكربت في الذاكرة.

لو أرجع السيرفر رد 404 Not Found، هل الكود هيدخل في الـ try ولا الـ catch؟

هيدخل في الـ try!
لأن fetch بتعتبر أي رد وصل من السيرفر بمثابة Promise ناجحة. عشان تخليه يدخل في الـ catch لازم تكتب بنفسك: if (!res.ok) throw new Error('Not Found');

5. تشريح دالة الـ Fetch النموذجية الإنتاجية · Code Anatomy

1: async function safeFetch(url, timeoutMs = 5000) { 2: const controller = new AbortController(); 3: const timer = setTimeout(() => controller.abort(), timeoutMs); 4: try { 5: const res = await fetch(url, { signal: controller.signal }); 6: if (!res.ok) throw new Error(`HTTP ${res.status}`); 7: return await res.json(); 8: } finally { 9: clearTimeout(timer); // Clean up memory 10: } 11: }

السطر 2 & 5: ربط إشارة controller.signal بطلب الـ Fetch للتحكم في قطعه برمجياً.

السطر 6: الفحص الحاسم لـ res.ok لضمان عدم تمرير أخطاء 404 أو 500 للواجهة.

السطر 9: مسح التايمر في كتلة finally لمنع تسريب الذاكرة.

7. أخطاء شائعة وفخاخ يقع فيها الجميع · Common Pitfalls

محاولة قراءة جسم الـ Response مرتين (Body Stream Locked)
// ❌ خطأ: يرمي TypeError: body stream already read
const data = await res.json();
const text = await res.text();
// ✅ استهلاك التدفق مرة واحدة فقط أو عمل Clone قبل القراءة
const clonedRes = res.clone();
const data = await res.json();

التشخيص الهندسي: تدفق الـ ReadableStream يتم تفريغه بمجرد قراءته ولا يمكن قراءته مرة أخرى إلا بنسخه عبر res.clone().

قاموس المصطلحات الأساسية · Mini-Glossary

AbortController
واجهة برمجية قياسية تمكنك من إلغاء عملية غير متزامنة (مثل طلب شبكة) في أي وقت قبل اكتمالها.
ReadableStream
تدفق تسلسلي للبيانات الثنائية يتم استقباله على أجزاء صغيرة (Chunks) متتالية بدلاً من الانتظار لتحميل الملف كله دفعة واحدة.

سؤال مقابلات شهير: إزاي تستخدم AbortController في React داخل useEffect؟

الإجابة الهندسية:
في React، تنشئ كائن const controller = new AbortController() داخل الـ Effect، وتمرر controller.signal لدالة fetch، وفي دالة التنظيف (Cleanup Function) الخاصة بالـ Effect تستدعي return () => controller.abort() لمنع تحديث الحالة على مكون تم إلغاء تركيبه (Unmounted) ومنع تسريب الذاكرة!
