Prisma Transactions & Concurrency: Interactive Transactions ($transaction) & Optimistic Locking

المعاملات والتزامن في Prisma: المعاملات التفاعلية ($transaction) والقفل التفاؤلي (Optimistic Locking)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • التمييز بين المعاملات المتسلسلة (Sequential $transaction([op1, op2])) والمعاملات التفاعلية (Interactive $transaction(async tx => {})).
  • تطبيق نمط القفل التفاؤلي (Optimistic Locking) باستخدام حقل رقم الإصدار version لمنع تعارض التعديلات المتزامنة.
  • ضبط إعدادات مهلة المعاملات وعزلها { maxWait: 5000, timeout: 10000, isolationLevel: "Serializable" }.
  • إدارة أخطاء P2025 (Record to update not found) ومعالجة التراجع التلقائي (Rollback).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في الأنظمة الإنتاجية الكبرى، المعاملات الذرية البسيطة ليست كافية عندما تحتاج لتنفيذ منطق برمجي معقد يعتمد على قراءة بيانات واتخاذ قرارات شرطية قبل الحفظ: تخيل نظام حجز تذاكر حفلات: 1. تقرأ عدد التذاكر المتبقية. 2. إذا كانت التذاكر المتبقية > 0، تخصم تذكرة وتنشئ سجل دفع. 3. إذا كانت التذاكر = 0، ترفض العملية وتعتذر للمستخدم. في **Prisma Interactive Transactions**، تتيح لك دالة prisma.$transaction(async (tx) => {}) تمرير نسخة عميل تفاعلية tx تضمن تنفيذ كل العمليات الشرطية داخل نفس اتصال قاعدة البيانات المقفول بـ ACID! بالإضافة إلى ذلك، في الأنظمة التي تفضل تجنب أقفال قواعد البيانات الثقيلة (High Concurrency APIs)، نطبق نمط **القفل التفاؤلي (Optimistic Concurrency Control)** باستخدام حقل version. في هذا الدرس، هنبني نظام دفع بنكي منيع، وهنتعلم إزاي نتحكم في مستويات العزل وضبط مهلات الـ Timeouts.

المعاملات المتسلسلة بـ $transaction([queries])

تمرير مصفوفة استعلامات لتنفيذها دفعة واحدة في رحلة شبكية موحدة؛ إما أن تنجح جميعها أو تفشل جميعها.

02

المعاملات التفاعلية بـ $transaction(async tx => {})

تنفيذ كود جافاسكريبت ومنطق شرطي داخل سياق المعاملة مع استخدام كائن tx الممرر حصراً.

03

نمط القفل التفاؤلي بـ Version Field

تحديث السجل بشرط تطابق رقم الإصدار where: { id, version: currentVersion } وزيادة الإصدار version: { increment: 1 }.

04

ضبط خيارات المعاملة (Timeouts & Isolation)

تحديد الحد الأقصى لانتظار الاتصال maxWait وزمن انتهاء المعاملة timeout لمنع تعليق الخادم.

05

معالجة التراجع التلقائي (Automatic Rollback)

أي استثناء أو Error يتم رميه داخل دالة الـ transaction يؤدي فوراً للتراجع التام وإلغاء التعديلات.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

export async function checkoutOrder(userId, total, items) { // دالة إتمام الشراء
  return await prisma.$transaction(async (tx) => { // 1. بدء المعاملة التفاعلية
    const wallet = await tx.wallet.findUnique({ where: { userId } }); // قراءة الرصيد عبر tx
    if (!wallet || wallet.balance < total) throw new Error("Insufficient Balance"); // فحص الرصيد
    await tx.wallet.update({                         // خصم الرصيد
      where: { userId }, data: { balance: { decrement: total } } // خصم ذري
    });                                              // نهاية الخصم
    const order = await tx.order.create({            // إنشاء الفاتورة
      data: { userId, total, items: { create: items } } // إنشاء متداخل
    });                                              // نهاية الإنشاء
    return order; // 2. تأكيد المعاملة تلقائياً      // Commit ناجح
  }, { maxWait: 3000, timeout: 8000 }); // 3. ضبط المهلات // إعدادات الأمان
}                                                    // نهاية الدالة

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ كارثي: استخدام prisma بدلاً من tx داخل دالة $transaction
await prisma.$transaction(async (tx) => {
  await tx.wallet.update(...);
  await prisma.order.create(...); // خطأ فادح: ينفذ خارج المعاملة ولن يتراجع عنه عند الخطأ!
});
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: استخدام كائن tx في جميع العمليات بلا استثناء
await prisma.$transaction(async (tx) => {
  await tx.wallet.update(...);
  await tx.order.create(...); // يضمن العزل والتراجع التام
});

التشخيص الهندسي: استخدام عميل prisma العام يتجاوز اتصال المعاملة المفتوح ويلغي حماية الـ Rollback، والواجب استخدام كائن tx فقط.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: متى تختار القفل التفاؤلي (Optimistic Locking) ومتى تختار القفل التشاؤمي (Pessimistic Locking بـ $queryRaw FOR UPDATE) في الأنظمة عالية الأحمال؟

نختار القفل التفاؤلي (Optimistic): عندما تكون نسبة التعديل المتزامن على نفس السجل نادرة (< 5% مثل تعديل الملفات الشخصية)، وهو ممتاز لأنه لا يفرض أي أقفال على الداتابيز ويحقق أقصى سرعة قراءة. نختار القفل التشاؤمي (Pessimistic): عندما تكون المنافسة شرسة ومؤكدة على مورد واحد في نفس الثانية (High Contention مثل بيع تذاكر حفل تنفد في 10 ثوانٍ أو مزادات حية)، لأن القفل التفاؤلي سيفشل 95% من الطلبات ويعيد المحاولات مما يرهق الـ CPU، بينما القفل التشاؤمي يصف الطلبات في طابور محكم.
