الفكرة الأساسية وسياق العالم الحقيقي

لماذا نحتاج هذا المفهوم وكيف يحل مشاكل الإنتاج المعقدة؟

في بيئات الإنتاج، عندما يشتكي عميل من بطء تحميل صفحته واستغراقها 3 ثوانٍ، كيف تعرف أي استعلام قاعدة بيانات بالتحديد تسبب في هذا التأخير؟ لو لم تكن تملك منظومة مراقبة (Observability & Tracing) دقيقة، ستظل تبحث في الظلام! يوفر **Prisma Client** نظام مراقبة متكامل عالي الأداء: 1. إمكانية الاستماع لأحداث الاستعلامات الحية بـ prisma.$on('query') واستخراج جملة الـ SQL الدقيقة وزمن التنفيذ بالـ Duration (ms). 2. الدعم الأصلي لمعيار **OpenTelemetry (OTel Tracing)**: يتيح تتبع رحلة الطلب بالكامل منذ دخوله مسار Express وحتى تنفيذه داخل PostgreSQL ورسم مخطط مائي كامل (Waterfall Trace) يوضح بالمللي ثانية أين ضاع الوقت. في هذا الدرس، هنبني طبقة مراقبة ورصد احترافية لخادمك، وهنتعلم إزاي نسجل الاستعلامات البطيئة في سجلات **Pino**.

📖 تشبيه واقعي من بيئة العمل الهندسية

طباعة كل استعلام في الـ Console ينشئ آلاف عمليات الإدخال والإخراج المتزامنة (Synchronous stdout writes) في Node.js، مما يحظر الـ Event Loop ويستهلك مساحة القرص الصلب في السيرفر بسرعة هائلة! في الإنتاج، نستخدم emit: "event" ونقوم بتسجيل الاستعلامات البطيئة فقط (Slow queries > 100ms) عبر مكتبة Logging لاتزامنية سريعة مثل Pino.

الميكانيكا العميقة: كيف يعمل خطوة بخطوة؟

تشريح تفصيلي لآلية العمل ومراحل التنفيذ داخل المحرك

01

تكوين مستويات السجلات (Log Levels)

تحديد log: [{ emit: "event", level: "query" }] للاستماع البرمجي لأحداث الاستعلامات.

02

اصطياد الاستعلامات البطيئة بـ $on("query")

تسجيل أي استعلام يتجاوز زمن تنفيذه e.duration > 100ms في نظام السجلات المركزي مع نص الـ SQL.

03

تفعيل التتبع الموزع بـ OpenTelemetry

تمكين previewFeatures = ["tracing"] في المخطط لتوليد Spans تلقائية متوافقة مع أنظمة Jaeger و Datadog.

04

ربط سياق الطلب (Trace ID Context Propagation)

ربط استعلامات قاعدة البيانات بـ Request ID الخاص بـ Express لتتبع كامل دورة حياة الطلب.

05

تطهير المعاملات الحساسة في السجلات

حجب كلمات المرور وأرقام البطاقات من السجلات قبل طباعتها لحماية خصوصية المستخدمين.

🚨 الكود الخاطئ / Anti-Pattern 
// خطأ شائع: تسجيل كافة الاستعلامات بـ console.log في خادم الإنتاج
const prisma = new PrismaClient({ log: ["query"] }); // يغرق السجلات بآلاف الأسطر ويبطئ المعالج!
✨ الكود الهندسي المعتمد / Best Practice 
// الحل الهندسي: استخدام emit: 'event' وفلترة الاستعلامات البطيئة فقط
const prisma = new PrismaClient({ log: [{ emit: "event", level: "query" }] });
prisma.$on("query", (e) => { if (e.duration > 100) logger.warn(e); });

سؤال إنترفيو للمهندسين الكبار: كيف تدمج Prisma Query Metrics داخل لوحات تحكم Prometheus و Grafana لمراقبة صحة الخوادم في الوقت الحقيقي؟

نستخدم واجهة prisma.$metrics.prometheus(): 1. ننشئ مساراً في Express باسم /metrics محمي بصلاحيات داخلية. 2. عند استدعائه، نطلب const metrics = await prisma.$metrics.prometheus(). 3. هذا يُرجع مقاييس قياسية فورية: عدد اتصالات الـ Connection Pool المفتوحة والنشطة (prisma_pool_connections_open / busy)، وزمن استجابة الاستعلامات (prisma_client_queries_duration_histogram_ms). 4. يقوم Prometheus بجمع هذه المقاييس كل 15 ثانية وعرضها على لوحة Grafana مع إطلاق تنبيهات فورية إذا ارتفع زمن الاستعلامات عن 200ms.
