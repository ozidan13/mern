Database Migrations & CI/CD Pipelines: prisma migrate, migrate deploy & Drift Detection

هجرات قواعد البيانات (Migrations) وخطوط الـ CI/CD: أوامر migrate و deploy واكتشاف الانجراف (Drift)

🎯 مخرجات التعلم وأهداف الدرس

  • ✓ فهم الفرق الجوهري بين npx prisma migrate dev (لبيئة التطوير) و npx prisma migrate deploy (لبيئات الإنتاج والـ CI/CD).
  • ✓ تشريح ملفات هجرات SQL المولدة وجدول التتبع المركزي _prisma_migrations.
  • ✓ كشف ومعالجة مشكلة انجراف قاعدة البيانات (Schema Drift Detection بـ prisma migrate diff).
  • ✓ بناء خطوط نشر مؤتمتة (GitHub Actions CI/CD) تطبق الهجرات بأمان دون التسبب في انقطاع الخدمة (Zero-Downtime Migrations).

الفكرة الأساسية وسياق العالم الحقيقي

لماذا نحتاج هذا المفهوم وكيف يحل مشاكل الإنتاج المعقدة؟

في المشاريع الفردية، يستخدم المطور prisma db push لتحديث قاعدة البيانات فورياً. لكن تشغيل prisma db push في بيئة الإنتاج هو جريمة معمارية قد تؤدي لحذف جداول وبيانات المستخدمين بضغطة زر واحدة (Data Loss Incident)! في بيئات العمل الاحترافية وخطوط الـ CI/CD، يتم تطبيق التعديلات عبر **هجرات SQL موثقة (Database Migrations)**: - كل تعديل في schema.prisma يولد ملف هجرة SQL مؤرخاً في مجلد prisma/migrations/. - هذه الملفات يتم مراجعتها في الـ Pull Requests ورفعها لـ Git. - عند النشر للإنتاج، يقوم خط الـ CI/CD بتشغيل أمر **npx prisma migrate deploy** الذي يقرأ الملفات المعتمدة فقط ويطبقها بترتيب صارم ومسجل في جدول _prisma_migrations. في هذا الدرس، هنبني خط نشر متكامل بـ GitHub Actions، وهنتعلم إزاي نكتشف **Schema Drift** ونطبق استراتيجية التحديثات دون انقطاع الخدمة (**Zero-Downtime Expand/Contract Pattern**).

📖 تشبيه واقعي من بيئة العمل الهندسية

أمر migrate dev هو أمر تفاعلي لبيئة التطوير: لو وجد أي تعارض، قد يطلب إعادة تصفير قاعدة البيانات (Reset Database) وحذف كافة البيانات! كما أن db push يتجاوز ملفات الهجرة ويعدل الجداول فوراً مما قد يحذف أعمدة مهمة. الأمر الوحيد المسموح بتشغيله في الإنتاج والـ CI/CD هو prisma migrate deploy لأنه يطبق الهجرات المسجلة فقط بشكل غير تفاعلي وآمن بنسبة 100%.

الميكانيكا العميقة: كيف يعمل خطوة بخطوة؟

تشريح تفصيلي لآلية العمل ومراحل التنفيذ داخل المحرك

01

توليد الهجرات بـ prisma migrate dev

مقارنة المخطط بقاعدة البيانات وتوليد ملف migration.sql وتطبيقه محلياً وتحديث أنواع العميل تلقائياً.

02

التطبيق الإنتاجي الصارم بـ prisma migrate deploy

أمر خطوط الـ CI/CD الذي يطبق الهجرات المعلقة فقط دون توليد ملفات جديدة ودون طلب أي مدخلات تفاعلية.

03

جدول التتبع الداخلي (_prisma_migrations)

تسجيل تاريخ ووقت وبصمة التجزئة (Checksum) لكل ملف هجرة لضمان عدم تطبيق نفس الهجرة مرتين.

04

كشف الانجراف بـ prisma migrate diff

مقارنة بنية قاعدة البيانات الحقيقية مع ملف المخطط لاكتشاف التعديلات اليدوية غير المصرح بها (Drift).

05

نمط التوسيع والانكماش (Expand/Contract Migration)

تعديل أسماء الأعمدة على مرحلتين لمنع انهيار الخوادم القديمة أثناء عملية الـ Rolling Update.

أخطاء الإنتاج القاتلة مقابل أفضل الممارسات

مقارنة بصرية واضحة بين الكود الكارثي والكود الهندسي المعتمد

🚨 الكود الخاطئ / Anti-Pattern 
// خطأ كارثي في الـ CI/CD: استخدام db push في الإنتاج
// RUN npx prisma db push --accept-data-loss
// يحذف الأعمدة المعدلة ويفقد بيانات العملاء دون أي سجل تراجع!
✨ الكود الهندسي المعتمد / Best Practice 
// الحل الهندسي المعتمد
// RUN npx prisma migrate deploy
// يطبق الهجرات المعتمدة والمراجعة في الـ Pull Requests بأمان تام
🔍 التشخيص المعماري للخلل

أمر db push غير مخصص للإنتاج ويسبب فقدان البيانات، بينما migrate deploy يطبق الهجرات المؤرخة المعتمدة فقط.

Real-World Architectural Interview Case

سؤال إنترفيو للمهندسين الكبار: كيف تحل مشكلة فشل هجرة إنتاجية في منتصف التنفيذ وظهور خطأ "Migration failed to apply cleanly"?

1. نفحص سجلات الـ CI/CD لمعرفة سبب فشل الهجرة بالتحديد (مثل وجود قيم NULL في عمود تم تحويله لـ NOT NULL). 2. نتصل بقاعدة البيانات ونفحص جدول _prisma_migrations ونصلح الخلل في بنية الـ SQL يدوياً. 3. نستخدم أمر npx prisma migrate resolve --rolled-back "migration_name" لإعلام Prisma بأن الهجرة تم التراجع عنها، أو --applied إذا قمنا بإكمالها يدوياً. 4. نصلح ملف الهجرة في الـ Git Repository ونعيد النشر بنظافة.
