Thinking in React: Component Hierarchy & State Flow

1. القصة والتشبيه الواقعي · The Core Story

تشبيه مكعبات الليجو وشجرة العائلة · Lego Blocks & Family Tree

تخيل إنك بتبني قلعة ضخمة من مكعبات الليجو.. بدل ما تصب القلعة كلها ككتلة إسمنت واحدة مستحيل تعدلها، بتبنيها من قطع صغيرة مستقلة: برج المراقبة، البوابة، والسور.
في ريآكت، كل قطعة من دول هي Component مستقل بذاته!
أما تدفق البيانات، فتخيل شجرة عائلة: الجد والوالد يقدروا يورثوا الأبناء هدايا وخصائص (Props) بتنزل من فوق لتحت في اتجاه واحد.. لكن لو في ابنين عايزين يشاركوا نفس اللعبة، الوالد (الأب المشترك) هو اللي بيحتفظ باللعبة عنده (Lifting State Up) ويديرها بينهم بعدل!

المشكلة التي حلتها ريآكت في تطوير الويب

في الطرق القديمة مع Vanilla JS أو jQuery، كنت لما تغير قيمة في مكان، بتضطر تدور يدوياً على كل عناصر الـ DOM اللي محتاجة تتحدث وتكتب document.getElementById() وتعدل الـ innerHTML. الكود كان بيتحول لعش دبابير متشابك (Spaghetti Code) ومستحيل تعرف مين غير إيه! ريآكت حلت الكارثة دي بالمعادلة الشهيرة: UI = f(State).. أنت بس بتعرف الحالة والـ JSX، وريآكت هي اللي بتحدث الـ DOM أوتوماتيكياً بأعلى كفاءة.

2. خطوات التفكير بعقلية ريآكت · The 5 Steps Breakdown

1
1. تفكيك التصميم إلى شجرة مكونات (Component Hierarchy)

ارسم مربعات حول كل جزء في التصميم وتأكد أن كل مكون يقوم بمهمة واحدة فقط (Single Responsibility Principle).

2
2. بناء النسخة الثابتة أولاً (Static Version with Props)

ابنِ شجرة المكونات بالـ JSX ومرر البيانات عبر الـ Props فقط بدون استخدام أي useState في البداية لضمان صحة البنية.

3
3. تحديد الحالة الأدنى الكافية (Minimal State Representation)

اسأل 3 أسئلة لأي متغير: هل هو ممرر من الأب؟ هل هو ثابت لا يتغير؟ هل يمكن حسابه من حالة أخرى؟ إذا كانت الإجابة نعم، فهو ليس State!

6. كواليس هندسية وتحليل الأداء · Deep Dive

نقاء الدوال (Component Purity)
Pure f(props)

مكونات ريآكت يجب أن تكون دوالاً نقية: نفس الـ Props ترجع دائماً نفس الـ JSX بدون أي Side Effects أثناء مرحلة الـ Render.

قاعدة الحالة المحسوبة
Derived State = 0 State

لا تنشئ useState أبداً لمتغير يمكن حسابه في نفس السطر (مثل const count = items.length).

7. أخطاء شائعة وفخاخ يقع فيها الجميع · Common Pitfalls

محاولة تعديل الـ Props مباشرة داخل المكون الفرعي
// ❌ كارثة: الـ Props للقراءة فقط (Read-Only)
function UserCard({ user }) {
  user.name = 'Ahmed'; // Mutation!
}
// ✅ استدعاء دالة رد النداء الممررة من الأب
function UserCard({ user, onUpdate }) {
  onUpdate({ ...user, name: 'Ahmed' });
}

التشخيص الهندسي: كائن الـ Props يتم تجميده في وضع Strict Mode، وأي تعديل مباشر عليه يكسر شجرة الـ Reconciliation ويعطل التحديثات.

قاموس المصطلحات الأساسية · Mini-Glossary

Props
البيانات والمعاملات الممررة من المكون الأب إلى المكون الابن وتكون دائماً غير قابلة للتعديل (Read-Only).
State
الذاكرة الحية الخاصة بالمكون التي عندما تتغير، تطلب من ريآكت إعادة رسم المكون (Re-render).

سؤال مقابلات شهير: إيه هو الـ Prop Drilling وإزاي بنحله في التطبيقات الكبيرة؟

الإجابة الهندسية:
الـ Prop Drilling هو تمرير الـ Props عبر 5 أو 6 طبقات من المكونات الوسيطة التي لا تحتاجها فقط لتوصيلها لمكون عميق في الأسفل. يتم حله عبر: 1. Component Composition (تمرير المكونات كـ children).
2. React Context API للبيانات العامة مثل المظهر واللغة وبيانات المستخدم المسجل.
3. مكتبات إدارة الحالة مثل Zustand أو Redux Toolkit.
