سر مبدأ الـ Immutability (عدم التعديل المباشر)

ريآكت عشان تعرف إن الحالة اتغيرت وتعمل Re-render، مش بتدخل تقارن كل عنصر في المصفوفة أو الكائن (وده هيكلف وقت هائل O(N)). ريآكت بس بتعمل فحص سريع للمرجع في الذاكرة: Object.is(oldState, newState). لو كتبت items.push(newItem)، المرجع في الذاكرة هيفضل هو هو، وريآكت هتقول: "مفيش حاجة اتغيرت" ومش هتعمل Render! عشان كده دايماً بنعمل نسخة جديدة تماماً باستخدام الـ Spread Operator: setItems([...items, newItem]).

5. تشريح تحديث الكائنات والمصفوفات بشكل نقي · Code Anatomy

1: const [user, setUser] = useState({ name: 'Omar', role: 'admin' }); 2: 3: function handleRoleChange(newRole) { 4: setUser(prevUser => ({ 5: ...prevUser, // 1. Copy old fields 6: role: newRole // 2. Override target field 7: })); 8: }

السطر 4: استخدام prevUser يضمن القراءة من أحدث حالة مسجلة في الـ Fiber.

السطر 5: الـ Spread Operator ...prevUser ينشئ كائناً جديداً تماماً في الذاكرة فيتغير المرجع وتفهم ريآكت التحديث فوراً.

6. كواليس هندسية وتحليل الأداء · Deep Dive

التهيئة الكسولة (Lazy Initial State)
useState(() => calc())

إذا كانت القيمة المبدئية تتطلب عملية حسابية ثقيلة (مثل قراءة localStorage)، مرر دالة لـ useState لتعمل في أول Render فقط وتوفر الـ CPU في باقي الـ Renders.

7. أخطاء شائعة وفخاخ يقع فيها الجميع · Common Pitfalls

تعديل المصفوفة المباشر (Direct State Mutation)
// ❌ خطأ: تعديل مباشر للمصفوفة لن يسبب Re-render
todos.push(newTodo);
setTodos(todos);
// ✅ إنشاء مصفوفة جديدة بالكامل عبر Spread
setTodos([...todos, newTodo]);

التشخيص الهندسي: دالة Object.is(todos, todos) تعيد true لأن المرجع متطابق، فتتجاهل ريآكت طلب الـ Render.

نفضل useReducer عندما:
1. تكون الحالة معقدة وتحتوي على عدة كائنات ومصفوفات مترابطة وتتغير بناءً على أحداث متعددة.
2. عندما تعتمد الحالة القادمة على حسابات معقدة من الحالة السابقة وتريد فصل منطق الأعمال (Business Logic) خارج المكون لاختباره بسهولة (Unit Testing).
