Lists, Keys & Reconciliation: Identity Preservation & Index Anti-Pattern

القوائم والمفاتيح في ريآكت: الحفاظ على هوية المكونات وفخ استخدام Index كـ Key

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم خوارزمية المطابقة (Reconciliation Algorithm) ودور الخاصية key في الحفاظ على هوية عقد Fiber.
  • تجنب الفخ الكارثي لاستخدام key={index} في القوائم القابلة للحذف أو الترتيب أو الفلترة.
  • استخدام crypto.randomUUID() أو معرفات قاعدة البيانات الثابتة لتأمين استقرار الـ State الداخلي.
  • معرفة متى تستخدم الخاصية key لإعادة تهيئة (Reset) حالة مكون ما قسرياً.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

كل مطور ريآكت رأى التحذير الشهير في الـ Console: Warning: Each child in a list should have a unique "key" prop. الحل السريع الذي يلجأ إليه المبتدئ هو كتابة items.map((item, index) => <Card key={index} />) لإخفاء التحذير. لكن هذا "الحل السريع" هو قنبلة موقوتة في تطبيقك! تخيل أن عندك قائمة مهام (Todo List) وكل عنصر فيه Checkbox أو Input لكتابة ملاحظات. عندما يحذف المستخدم العنصر الأول من القائمة، ماذا يحدث؟ ريآكت تقارن القائمة القديمة بالجديدة بناءً على الـ Keys (0, 1, 2). وبما أن العنصر الثاني أصبح يحمل index = 0، ستعتقد ريآكت أن العنصر الأول لم يُحذف بل تم تعديل نصوصه فقط، وستحتفظ بالـ State الداخلي للعنصر الأول (الـ Checkbox المعلم) وتنطله للعنصر الجديد! في هذا الدرس، هنغوص في خوارزمية الـ Diffing في ريآكت، وهنفهم ليه الـ Key هو "بطاقة الهوية الوطنية" لكل مكون في شجرة الـ Fiber.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

خوارزمية مطابقة القوائم O(n)

تعتمد ريآكت على الـ Keys لمطابقة العناصر القديمة بالجديدة لتفادي إعادة بناء شجرة الـ DOM بالكامل O(n^3).

02

كارثة استخدام Index كـ Key

عند الحذف أو الترتيب، تتغير أرقام الـ Index لكل العناصر اللاحقة، مما يربك ريآكت ويؤدي لتسريب الـ State الداخلي (Uncontrolled Inputs, Animations).

03

شروط الـ Key المثالي

يجب أن يكون فريداً بين أشقائه (Unique among siblings)، ثابتاً لا يتغير مع كل Render (Stable)، ومرتبطاً بهوية البيانات الفعلية (مثل item.id).

04

إعادة تهيئة المكون قسرياً بـ Key Reset

تغيير قيمة key على مكون عادي يجبر ريآكت على حذف المكون القديم وإنشاء نسخة جديدة تماماً بـ State مصفى.

05

توليد المفاتيح المؤقتة بأمان

استخدم crypto.randomUUID() فقط عند إنشاء العنصر وتخزينه في الـ State، ولا تولد أرقاماً عشوائية Math.random() داخل جملة الـ map مباشرة.

مع كل عملية إعادة رسم (Re-render)، سيتم توليد مفتاح عشوائي جديد تماماً لكل عنصر. ريآكت ستعتقد أن جميع العناصر القديمة قد حُذفت وأن عناصر جديدة تماماً ظهرت، مما يدمر أداء التطبيق، ويلغي التركيب والتأثيرات الحركية (CSS Transitions)، ويفقد جميع مدخلات المستخدم والـ Focus في الحقول.

const UserList = ({ users, onDelete }) => (       // مكون القائمة
  <ul className="user-list">                   // عنصر القائمة
    {users.map(user => (                          // المرور على العناصر
      <UserRow                                    // المكون الفرعي
        key={user.id}                                // مفتاح ثابت وفريد مستمد من معرف البيانات
        user={user}                                  // تمرير البيانات
        onDelete={onDelete}                          // تمرير الدالة
      />                                          // إغلاق المكون
    ))}                                              // نهاية التحويل
  </ul>                                        // إغلاق القائمة
);                                                   // نهاية المكون

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع جداً: استخدام index كـ key في قائمة ديناميكية قابلة للتعديل
<ul>
  {todos.map((todo, index) => (
    <TodoItem key={index} text={todo.text} />
  ))}
</ul>
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: استخدام المعرف الفريد الدائم
<ul>
  {todos.map(todo => (
    <TodoItem key={todo.id} text={todo.text} />
  ))}
</ul>

التشخيص الهندسي: استخدام index كـ key يجعل المفاتيح تعتمد على موضع العنصر في المصفوفة وليس على هويته. عند الحذف أو إعادة الترتيب، تفشل خوارزمية المطابقة في تتبع الحالة الداخلية للمكونات الفرعية.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: اشرح كيف تستخدم ريآكت بنية الـ Fiber Linked List للمطابقة ومقارنة الأشقاء (Child Reconciler) عندما يكون للعناصر Keys ثابتة؟

في معمارية React Fiber، يتم تمثيل العناصر كشجرة عقد مترابطة (Singly Linked List: child, sibling, return). عند مطابقة مصفوفة من العناصر، تقوم ريآكت بإنشاء خريطة Map مؤقتة مفاتيحها هي الـ keys وقيمها هي عقد الـ Fiber القديمة. عندما تمر على العناصر الجديدة، تقوم بالبحث السريع O(1) في الـ Map بالاعتماد على الـ Key، فإذا وجدته تقوم بإعادة استخدام نفس عقدة الـ Fiber والـ DOM Node الحقيقي وتحرك موضعه فقط (Placement)، مما يوفر تكلفة إنشاء عناصر DOM جديدة ويحقق أقصى أداء ممكن.
