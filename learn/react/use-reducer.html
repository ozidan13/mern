useReducer: Complex State Machines, Discriminated Unions & Lazy Init

خطاف useReducer: آلات الحالة المعقدة (State Machines)، والتهيئة الكسولة (Lazy Init)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم متى تختار useReducer كبديل معماري متفوق لـ useState في إدارة الحالات المتشابكة.
  • تصميم دوال Reducers نقية (Pure Functions) باستخدام نمط Discriminated Unions في جافاسكريبت و TypeScript.
  • تطبيق مبدأ استحالة الحالات غير الصالحة (Making Impossible States Impossible).
  • استخدام المعامل الثالث (Lazy Initializer) لحساب الحالة الابتدائية الثقيلة بكفاءة.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

عندما تبني استمارة معقدة (Multi-step Form) أو شاشة تداول، تجد نفسك تكتب 6 أو 7 خطافات useState منفصلة: 

const [isLoading, setIsLoading] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);
الكارثة هنا هي "الحالات المستحيلة" (Impossible States): من الممكن برمجياً بسبب خطأ غير مقصود أن تصبح isLoading: true و error: "Failed" و isSuccess: true في نفس اللحظة! الواجهة ستصاب بالجنون: هل تعرض الـ Spinner أم رسالة الخطأ أم شاشة النجاح؟ خطاف useReducer يعالج هذه الفوضى بتحويل إدارة الحالة إلى **آلة حالة محدودة (Finite State Machine)** منضبطة. الحالة تتغير فقط عبر إرسال "أفعال صريحة" (Dispatched Actions)، ودالة الـ Reducer تضمن الانتقال الصارم من حالة إلى أخرى، مما يجعل اختبار المنطق مستقلاً تماماً عن واجهة المستخدم.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

عقد دالة الـ Reducer النقية

دالة نقية تستقبل الحالة الحالية والإجراء (state, action) وتُرجع الحالة الجديدة فقط بدون أي آثار جانبية (No Side Effects/No API Calls).

02

هيكلة الإجراءات بـ Action Objects

كل إجراء يحمل نوعاً مميزاً { type: "FETCH_SUCCESS", payload: responseData } لتحديد مسار التحول.

03

إرسال الإجراءات عبر dispatch()

دالة dispatch مستقرة المرجع ولا تتغير بين عمليات الـ Render، مما يجعلها آمنة للتمرير للمكونات الفرعية بدون إعادة رسم.

04

التهيئة الكسولة (Lazy Initialization via init)

تمرير دالة كمعامل ثالث useReducer(reducer, initialArg, init) لحساب الحالة الابتدائية المعقدة مرة واحدة فقط عند التركيب.

05

منع تعديل الحالة المباشر (Immutable State Updates)

استخدام Spread Operator return { ...state, count: state.count + 1 } لضمان تغيير المرجع واستشعار ريآكت للتحديث.

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

في بيئة Strict Mode وميزات Concurrent React (مثل startTransition أو Suspense)، قد تقوم ريآكت باستدعاء دالة الـ Reducer عدة مرات لحساب الفروق دون تطبيق التحديث فعلياً. إذا كانت الدالة تحتوي على آثار جانبية مثل استدعاء API أو تعديل متغير عام، ستتكرر هذه العمليات بشكل غير متوقع وتحدث تسريبات وكوارث في البيانات.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

const [state, dispatch] = useReducer(reducer, initialArg, init); // تهيئة خطاف useReducer مع دالة init الكسولة
dispatch({ type: "CART_ADD_ITEM", payload: newItem }); // إرسال إجراء محدد مع البيانات
function reducer(state, action) {                    // دالة التحويل النقية
  switch (action.type) {                             // فحص نوع الإجراء
    case "CART_ADD_ITEM":                            // معالجة إضافة عنصر
      return { ...state, items: [...state.items, action.payload] }; // تحديث غير تعديلي لإنتاج كائن جديد
    default:                                         // الحالة الافتراضية
      return state;                                  // إرجاع الحالة كما هي
  }                                                  // نهاية التبديل
}                                                    // نهاية الـ Reducer

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ كارثي: تعديل الحالة الأصلية مباشرة داخل الـ Reducer
case "ADD_TODO":
  state.todos.push(action.payload); // Mutation مباشر يدمر ريآكت!
  return state; // المرجع لم يتغير ولن يحدث Re-render
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: إنتاج مصفوفة جديدة وكائن جديد
case "ADD_TODO":
  return {
    ...state,
    todos: [...state.todos, action.payload]
  }; // مرجع جديد يضمن تحديث الواجهة بنجاح

التشخيص الهندسي: محرك ريآكت يقارن الحالة السابقة بالجديدة بـ Object.is(oldState, newState). تعديل المصفوفة بالـ push يغير المحتوى الداخلي مع بقاء نفس المرجع، فتتجاهل ريآكت التحديث.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تنفذ نمط Reducer Composition لتقسيم Reducer ضخم يحتوي على 50 حالة إلى Reducers فرعية معيارية ونظيفة؟

نطبق نمط Reducer Composition بإنشاء Root Reducer يستدعي دوال Reducers فرعية متخصصة (مثل userReducer, cartReducer, uiReducer)، حيث يستقبل كل Reducer فرعي الجزء الخاص به فقط من الحالة return { user: userReducer(state.user, action), cart: cartReducer(state.cart, action) }. هذا النمط يحاكي دالة combineReducers الشهيرة في Redux ويحافظ على نقاء وسهولة اختبار وصيانة كل فرع من فروع الحالة بشكل مستقل تماماً.
