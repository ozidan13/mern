في MongoDB، كل مريض له ملف شامل واحد محفوظ في درج واحد (BSON Document):
بتسحب الملف، تلاقي الاسم، والعنوان مدمج جواه (Embedded Address)، وتاريخ الزيارات السابقة، وكل حاجة جاهزة في قراءة قرصية واحدة فورية O(1)!

المشكلة التي حلتها قواعد بيانات المستندات

في تطبيقات الويب الحديثة (MERN Stack)، البيانات بتتحرك في JavaScript ككائنات JSON. قواعد البيانات العلائقية كانت بتجبرك تفكك الكائن لـ 5 جداول منفصلة (Object-Relational Impedance Mismatch). مونجو دي بي ألغت هذه الفجوة: الكائن في كودك هو نفسه الوثيقة المخزنة في قاعدة البيانات بنفس البنية والـ Polymorphism!

2. كواليس تخزين ونمذجة الـ BSON · Step-by-Step Mechanics

1
1. بنية الـ BSON الثنائية (Binary JSON)

تخزن مونجو البيانات كـ BSON ثنائي يحتوي على طول الحقول ونوع البيانات، مما يتيح لمحرك WiredTiger التنقل السريع دون قراءة كامل الوثيقة.

2
2. نمط التضمين (Embedding Pattern: 1-to-Few)

نستخدم التضمين عندما تكون البيانات الفرعية تابعة حصرياً للأب ولا تزيد عن بضع عشرات (مثل عناوين الشحن أو خيارات المنتج).

3
3. نمط الإسناد (Referencing Pattern: 1-to-Many / Unbounded)

نستخدم الإسناد بتخزين ObjectId فقط عندما تكون البيانات تنمو بشكل لا نهائي (مثل سجلات المراقبة Logs أو تعليقات المقالات الضخمة).

تخزين البيانات المرتبطة معاً في مسار قرص متجاور (Contiguous Disk Blocks) يمنع الـ Random I/O ويضاعف سرعة الاستعلامات.

وضعت MongoDB حد الـ 16MB لحماية الـ RAM والشبكة من وثائق عملاقة تجمد محرك الـ Query Engine.

7. أخطاء شائعة وفخاخ يقع فيها الجميع · Common Pitfalls

الاستعلام بدون فهارس مركبة (Collection Scan COLLSCAN)
// ❌ بطيء جداً: يقرأ مليون وثيقة في الرام عند البحث بالبريد والحالة
db.users.find({ email: 'x@x.com', active: true });
// ✅ إنشاء فهرس مركب يجعل البحث في 0ms باستخدام B-Tree
db.users.createIndex({ email: 1, active: 1 });

التشخيص الهندسي: غياب الفهرس يجبر محرك WiredTiger على مسح كل صفحة في القرص (COLLSCAN)، بينما الفهرس يعيد النتيجة في O(log N).

سؤال مقابلات شهير: إمتى تستخدم MongoDB وإمتى تستخدم PostgreSQL؟

الإجابة الهندسية:
- نختار MongoDB عندما: تكون البيانات غير متجانسة ومتغيرة البنية باستمرار (Polymorphic Catalogs)، أو عند الحاجة لتوسيع أفقي فائق السهولة (Horizontal Sharding) لكميات بيانات ضخمة.
- نختار PostgreSQL عندما: تكون البيانات مترابطة بشكل معقد وعميق (Financial / Banking Systems) وتتطلب ضمانات ACID صارمة جداً وسلامة علاقات Foreign Keys محكمة.
