Indexing Architecture: Compound Indexes, ESR Rule, Partial & TTL Indexes

معمارية الفهارس: الفهارس المركبة (Compound)، قاعدة ESR الذهبية وفهارس TTL

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم البنية الشجرية للفهارس (B-Tree Data Structure) في محرك WiredTiger والفرق بين COLLSCAN و IXSCAN.
  • إتقان تطبيق قاعدة ESR الذهبية (Equality, Sort, Range) لبناء فهارس مركبة تحقق أعلى كفاءة.
  • تطبيق الفهارس الجزئية (Partial Indexes) والفهارس النادرة (Sparse Indexes) لتوفير حجم الذاكرة.
  • بناء فهارس الحذف التلقائي (TTL Indexes) لإزالة الجلسات والسجلات المؤقتة بعد انقضاء وقت محدد.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

لو كان لديك جدول يحتوي على 5 ملايين مستخدم، ونفذت استعلاماً بدون فهرس مناسب: db.users.find({ status: "active", age: { $gte: 21 } }).sort({ createdAt: -1 }) سيقوم محرك MongoDB بفحص جدول كامل (Collection Scan - COLLSCAN): سيقرأ الـ 5 ملايين مستند بالكامل من القرص الصلب إلى الـ RAM، وسيحاول فرزها في الذاكرة (In-Memory Sort)، فإذا تجاوز حجم الفرز سقف 32MB، سينهار الاستعلام فوراً بخطأ: 

Executor error during sort: Sort memory limit exceeded.
الحل المعماري هو بناء الفهارس المركبة (Compound Indexes) وفق **قاعدة ESR الذهبية (Equality, Sort, Range)**. الفهرس هو شجرة B-Tree مرتبة في الذاكرة تسمح للمحرك بالقفز مباشرة إلى النتائج المطابقة في 1ms وبدون أي مسح للمستندات غير المطلوبة. في هذا الدرس، هنفكك مخططات التنفيذ بـ explain("executionStats")، وهنتعلم إزاي نبني **Partial Indexes** و **TTL Indexes**.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

تشريح خطة التنفيذ بـ explain("executionStats")

مقارنة totalDocsExamined مع nReturned؛ الفهرس المثالي يفحص عدداً مساوياً تماماً للنتائج المسترجعة.

02

قاعدة ESR الذهبية للفهارس المركبة

ترتيب حقول الفهرس الصارم: أولاً حقول التطابق التام (Equality)، ثانياً حقول الترتيب (Sort)، وأخيراً حقول النطاق والمقارنات (Range).

03

الفهارس المغطاة (Covered Queries)

عندما تكون جميع الحقول المطلوبة في الـ Projection موجودة في الفهرس، يُرجع MongoDB النتيجة من RAM الفهرس دون لمس القرص نهائياً.

04

الفهارس الجزئية (Partial Indexes)

فهرسة المستندات التي تحقق شرطاً معيناً فقط { partialFilterExpression: { status: "active" } } لتوفير مساحة الـ RAM.

05

فهارس الحذف التلقائي بـ TTL (Time-To-Live)

تعيين { expireAfterSeconds: 3600 } على حقل تاريخي ليقوم المحرك بحذف السجلات المنتهية تلقائياً في الخلفية.

إذا وضعت حقل الـ Range أولاً { price: 1, createdAt: -1 }، فبمجرد أن يقوم محرك قاعدة البيانات بمسح نطاق الأسعار، ستكون التواريخ داخل كل نطاق غير مرتبة بالنسبة للمحرك! النتيجة: سيفشل الفهرس في تغطية الترتيب، وسيضطر MongoDB لتحميل المستندات في ذاكرة الـ RAM والقيام بعملية فرز في الذاكرة (In-Memory Sort / Blocking Sort) مما يبطئ الاستعلام بمئات المرات.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

// إنشاء فهرس مركب متوافق مع قاعدة ESR               // تطبيق قاعدة Equality -> Sort -> Range
await db.collection("orders").createIndex(           // أمر إنشاء الفهرس
  { customerId: 1, createdAt: -1, totalAmount: 1 }, // E -> S -> R // ترتيب الحقول الهندسي
  { name: "idx_orders_esr_lookup" }                  // تسمية الفهرس
);                                                   // نهاية الفهرس المركب
// إنشاء فهرس TTL لحذف الجلسات المؤقتة بعد 24 ساعة   // حذف تلقائي
await db.collection("sessions").createIndex(         // فهرس الجلسات
  { lastActivity: 1 },                               // حقل التاريخ
  { expireAfterSeconds: 86400 } // 24 ساعة           // مدة البقاء
);                                                   // نهاية فهرس TTL

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: إنشاء فهارس فردية لكل حقل على حدة
db.orders.createIndex({ customerId: 1 });
db.orders.createIndex({ createdAt: -1 });
db.orders.createIndex({ totalAmount: 1 });
// يستهلك RAM مضاعفة ولا يغطي الاستعلامات المركبة بكفاءة!
✅ الحل الهندسي القياسي (Best Practice)
// الحل الهندسي: فهرس مركب واحد ذكي يخدم الاستعلام الكامل
db.orders.createIndex({ customerId: 1, createdAt: -1, totalAmount: 1 });

التشخيص الهندسي: الفهارس الفردية لا توفر حلاً للاستعلامات التي تجمع بين التصفية والترتيب، بينما الفهرس المركب يخدم الاستعلام في مسح شجري واحد.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تكشف الفهارس غير المستخدمة (Unused Indexes) في خادم إنتاجي وتتخذ قرار حذفها بأمان؟

نستخدم استعلام $indexStats في الـ Aggregation Pipeline: db.collection.aggregate([{ $indexStats: {} }]). هذا الاستعلام يُرجع إحصائيات دقيقة لعدد مرات استخدام كل فهرس (accesses.ops) وتاريخ آخر استخدام (accesses.since). إذا كان الفهرس يملك ops: 0 لفترة طويلة (مثلاً 30 يوماً)، نقوم أولاً بإخفاء الفهرس بـ db.collection.hideIndex("idx_name") لمراقبة هل ستتأثر أي استعلامات في الإنتاج، وبعد التأكد من عدم تأثر الأداء، نقوم بحذفه نهائياً بـ dropIndex لتوفير مساحة الـ RAM وتسريع عمليات الـ Insert والـ Update.
