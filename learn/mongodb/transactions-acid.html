Multi-Document ACID Transactions, Write Concerns & Read Concerns

المعاملات متعددة المستندات (ACID Transactions): ضمانات الكتابة (Write Concern) والقراءة (Read Concern)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم خصائص الـ ACID الكاملة (Atomicity, Consistency, Isolation, Durability) في MongoDB عبر عدة مستندات ومجموعات.
  • تطبيق نمط جلسات المعاملات ClientSession مع بروتوكول withTransaction لإعادة المحاولة التلقائية عند أخطاء TransientTransactionError.
  • فهم مستويات ضمانات الكتابة: w: 1, w: "majority", و j: true (Journaling).
  • فهم مستويات ضمانات القراءة: local, majority, و linearizable لمنع قراءة البيانات غير المؤكدة (Dirty Reads).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في الأنظمة المالية وتطبيقات التجارة الإلكترونية، هناك عمليات لا تقبل أنصاف الحلول: عندما يقوم عميل بتحويل 1000 دولار من حسابه لشراء منتج: 1. يجب خصم 1000 دولار من جدول wallets. 2. يجب إضافة 1000 دولار لحساب التاجر. 3. يجب تقليل كمية المخزون في جدول products. 4. يجب إنشاء فاتورة جديدة في جدول invoices. لو نجحت الخطوة 1 وفشلت الخطوة 3 بسبب انقطاع الشبكة، سيخسر العميل أمواله دون استلام المنتج! منذ إصدار MongoDB 4.0 ووصولاً لـ MongoDB 8، تدعم قواعد MongoDB **المعاملات متعددة المستندات (Multi-Document Distributed ACID Transactions)** بالكامل! إما أن تنجح جميع العمليات الأربع معاً، أو يتم التراجع عنها بالكامل (Rollback) وكأن شيئاً لم يكن. في هذا الدرس، هنتعلم إزاي نبني معاملات بنكية منيعة بـ withTransaction()، ونفهم إعدادات **Write Concern** و **Read Concern** لضمان متانة البيانات.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

بدء الجلسة الذرية بـ client.startSession()

إنشاء جلسة عمل تربط العمليات المتعددة في سياق معاملة واحدة متصلة عبر خوادم الـ Replica Set.

02

بروتوكول withTransaction المدمج

استخدام withTransaction لإدارة Commit و Abort تلقائياً مع إعادة المحاولة التلقائية عند تعارض العمليات المتزامنة.

03

ضمانات الكتابة الموثوقة بـ Write Concern majority

اشتراط تأكيد كتابة البيانات على أغلبية خوادم الـ Replica Set قبل إرجاع رسالة النجاح للعميل لمنع فقدان البيانات.

04

التسجيل في سجل العمليات بـ Journaling (j: true)

ضمان كتابة المعاملة في ملف الـ Journal على القرص الصلب لضمان استرجاعها حتى لو انقطعت الكهرباء عن السيرفر فوراً.

05

عزل القراءات بـ Read Concern snapshot

قراءة البيانات من لقطة زمنية متناسقة تضمن عدم رؤية تعديلات المعاملات الأخرى غير المكتملة (Dirty Reads).

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

تعتمد المعاملات في MongoDB على سجل العمليات الموزع (Oplog - Operations Log) وإجماع الأغلبية (Consensus Protocol) لتنسيق وتثبيت التعديلات والتحقق من متانة البيانات. خوادم الـ Standalone لا تحتوي على Oplog، ولذلك تتطلب MongoDB تشغيل Replica Set (حتى لو كانت بمجموعة محلية من عقدة واحدة) لتفعيل محرك المعاملات.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

import { MongoClient } from "mongodb";               // عميل MongoDB الرسمي
export async function transferFunds(client, fromUser, toUser, amount) { // دالة التحويل البنكي
  const session = client.startSession();             // 1. بدء الجلسة
  try {                                              // كتلة التنفيذ
    await session.withTransaction(async () => {   // 2. بروتوكول المعاملة الذاتية
      const wallets = client.db("bank").collection("wallets"); // مجموعة المحافظ
      await wallets.updateOne({ userId: fromUser }, { $inc: { balance: -amount } }, { session }); // خصم المبلغ مع تمرير الجلسة
      await wallets.updateOne({ userId: toUser }, { $inc: { balance: amount } }, { session }); // إيداع المبلغ مع تمرير الجلسة
    }, { writeConcern: { w: "majority", j: true } }); // 3. ضمانات الكتابة الصارمة
  } finally {                                        // ضمان التحرير
    await session.endSession(); // 4. إغلاق الجلسة دائماً // تحرير الموارد
  }                                                  // نهاية الدالة
}                                                    // نهاية الكود

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: نسيان تمرير كائن { session } في استعلامات المعاملة
await wallets.updateOne({ userId: fromUser }, { $inc: { balance: -amount } }); // لن يكون جزءاً من المعاملة وسينفذ فوراً خارجها!
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: تمرير { session } في كل استعلام داخل المعاملة
await wallets.updateOne({ userId: fromUser }, { $inc: { balance: -amount } }, { session });

التشخيص الهندسي: أي استعلام لا يتم تمرير { session } إليه سيعامل كاستعلام مستقل ولن يتم التراجع عنه إذا حدث Rollback للمعاملة.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: ما هو الفرق المعماري بين نمطين: 1. الاعتماد على Multi-document Transactions في كل عملية، 2. تصميم المخطط بنمط Single Document Atomicity، ولماذا تفضل المنظومات فائقة السرعة النمط الثاني؟

في MongoDB، أي تعديل على مستند واحد هو عملية ACID ذرية بطبيعتها (Single-Document Atomicity) بدون أي تكلفة إضافية (0% Overhead). المعاملات متعددة المستندات (Multi-Document Transactions) تتطلب قفل سجلات متعددة وتنسيق عبر عقد الـ Replica Set، مما يضيف زمناً وتكلفة معالجة (Latency Overhead). لذلك، في المنظومات عالية الأحمال (High-throughput systems)، نقوم بتصميم المخططات بذكاء عبر التضمين (Embedding) لتكون 90% من العمليات الحيوية داخل مستند واحد ذري، ونحصر استخدام Multi-document Transactions فقط في العمليات المالية البنكية المعقدة التي تشمل جداول مستقلة.
