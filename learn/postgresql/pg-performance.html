PostgreSQL Performance Tuning: EXPLAIN ANALYZE, Memory Config & Connection Pooling

تحسين أداء PostgreSQL: تشريح EXPLAIN ANALYZE، ضبط الذاكرة (shared_buffers) ومجمعات PgBouncer

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • تشريح خطة تنفيذ الاستعلامات بـ EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS) وكشف تكاليف الـ Cost والمؤشرات الحقيقية.
  • ضبط معايير الذاكرة الجوهرية في postgresql.conf: shared_buffers, work_mem, maintenance_work_mem, و effective_cache_size.
  • حل معضلة استهلاك اتصالات الـ Backend (Process-per-connection) باستخدام مجمع الاتصالات الخفيف PgBouncer.
  • تفعيل امتداد pg_stat_statements لاصطياد أبطأ وأكثر الاستعلامات استهلاكاً لموارد السيرفر في بيئة الإنتاج.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في خوادم الإنتاج الكبرى، عندما يشتكي المستخدمون من بطء الموقع، يقوم المطور المبتدئ بمضاعفة حجم السيرفر (Upgrading Cloud Tier)، ليكتشف بعد يومين أن السيرفر عاد للبطء مجدداً وتضاعفت الفاتورة الشهرية! السبب هو أن الإعدادات الافتراضية لـ PostgreSQL في ملف postgresql.conf صُممت تاريخياً لتعمل على أجهزة قديمة جداً بـ 128MB RAM فقط! لو كان سيرفرك يمتلك 64GB RAM، فإن بوستجريس لن تستخدم افتراضياً سوى 128MB لذاكرة الـ shared_buffers وتترك باقي الـ RAM نائمة! بالإضافة إلى ذلك، كل اتصال جديد في PostgreSQL ينشئ عملية نظام تشغيل منفصلة (Forked OS Process) تستهلك ~10MB من الـ RAM؛ لو اتصل 1000 مستخدم في نفس اللحظة، سينهار الخادم فوراً باستهلاك الذاكرة. الحل المعماري هو: 1. ضبط معايير الذاكرة الاحترافية (shared_buffers = 25% RAM, work_mem). 2. وضع مجمع اتصالات فائق الخفة **PgBouncer** أمام قاعدة البيانات. 3. تشخيص الاستعلامات بـ **EXPLAIN ANALYZE** وامتداد **pg_stat_statements**. في هذا الدرس الختامي لمسار PostgreSQL 18، هنتعلم إزاي نحول خادمك إلى آلة فائقة السرعة تتحمل ملايين العمليات.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

تشريح خطة التنفيذ بـ EXPLAIN (ANALYZE, BUFFERS)

مقارنة التكلفة التقديرية (cost) بالزمن الفعلي (actual time) وعدد صفحات الذاكرة المقروءة من الكاش (Buffers: shared hit).

02

ضبط ذاكرة التخزين المؤقت (shared_buffers)

تخصيص 25% من إجمالي ذاكرة السيرفر لـ shared_buffers لتخزين الجداول والفهارس النشطة في الـ RAM.

03

ضبط ذاكرة الفرز والعمليات (work_mem)

تخصيص ذاكرة مخصصة لكل عملية فرز (Sort) أو دمج (Hash Join) لمنع تسريب العمليات إلى القرص الصلب (Spilling to Disk).

04

تجميع الاتصالات المليوني بـ PgBouncer (Transaction Pooling)

إدارة 10,000 اتصال من تطبيقات Node.js وتمريرها عبر 50 اتصالاً حقيقياً فقط لقاعدة البيانات بأعلى كفاءة.

05

مراقبة الاستعلامات التراكمية بـ pg_stat_statements

تسجيل وتجميع أزمنة تنفيذ جميع استعلامات النظام وتحديد الاستعلامات التي تستهلك أكثر من 80% من وقت المعالج.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

-- تفعيل وتشخيص أبطأ 5 استعلامات عبر pg_stat_statements // أداة الرصد المركزية
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;   // تثبيت الامتداد
SELECT                                               // استعلام التحليل
  query, calls,                                      // نص الاستعلام وعدد مرات استدعائه
  ROUND(total_exec_time::numeric, 2) as total_time_ms, // إجمالي الوقت المستهلك
  ROUND(mean_exec_time::numeric, 2) as avg_time_ms,  // متوسط زمن التنفيذ
  ROUND((100 * total_exec_time / SUM(total_exec_time) OVER())::numeric, 2) as percentage // النسبة المئوية من إجمالي وقت السيرفر
FROM pg_stat_statements                              // جدول الإحصائيات
ORDER BY total_exec_time DESC                        // فرز بالأكثر استهلاكاً
LIMIT 5;                                             // أعلى 5 اختناقات

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: فتح 1000 اتصال مباشر من خوادم Node.js بدون PgBouncer
// كل اتصال يستهلك 10MB RAM وتتنافس 1000 عملية على الـ CPU مما يؤدي لـ Context Switching وتجمد السيرفر!
✅ الحل الهندسي القياسي (Best Practice)
// الحل المعماري: استخدام PgBouncer في نمط Transaction Pooling
// 1000 اتصال من Node.js -> PgBouncer -> 30 اتصال فقط لـ PostgreSQL بأقصى سرعة

التشخيص الهندسي: الخوادم تنهار بكثرة الاتصالات المباشرة، بينما PgBouncer يثبت عدد الاتصالات الفعلية ويوجه الطلبات عبر طابور فائق الكفاءة.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تحلل استعلاماً بطيئاً في الإنتاج باستخدام EXPLAIN (ANALYZE, BUFFERS) وتكتشف أين يضيع الوقت بالضبط؟

1. نفحص Actual Time في العقدة الجذرية لمعرفة إجمالي زمن التنفيذ بالمللي ثانية. 2. نبحث عن أي عقدة تحتوي على Seq Scan على جدول كبير أو Filter حذف نسبة ضخمة من الصفوف (Rows Removed by Filter)، مما يدل على غياب الفهرس. 3. نفحص Buffers: shared read مقارنة بـ shared hit لمعرفة هل الاستعلام يقرأ من القرص البطيء أم من كاش الذاكرة. 4. نفحص أسلوب الفرز Sort Method: إذا وجدنا external merge Disk، فهذا يعني أن work_mem غير كافية ويجب زيادتها لتتم العملية في الـ RAM فورياً (quicksort memory).
