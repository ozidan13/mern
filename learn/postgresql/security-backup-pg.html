PostgreSQL Production Security: Row-Level Security (RLS), pg_dump & WAL Archiving

أمان وتأمين PostgreSQL: أمان مستوى الصف (RLS)، النسخ بـ pg_dump وأرشفة WAL

  • تفعيل وتطبيق سياسات الأمان على مستوى الصف (Row-Level Security: RLS Policies).
  • تنفيذ النسخ الاحتياطي المتناسق بـ pg_dump (Custom Directory & Tar formats).
  • فهم معمارية الـ Write-Ahead Logging (WAL) والاسترجاع لأي نقطة زمنية (PITR).

المشكلة الهندسية والسياق الواقعي

رؤية الواقع العملي · Real-World Context & Mental Model

حماية قاعدة البيانات في الإنتاج تتجاوز كلمات السر المشفرة. ميزة Row-Level Security (RLS) في PostgreSQL تقدم أماناً ثورياً على مستوى المحرك: حتى لو استطاع العميل استدعاء SELECT * FROM documents، فإن المحرك لن يُرجع له سوى الصفوف التي يمتلك صلاحيتها فقط! بالإضافة إلى استراتيجيات استرجاع الكوارث الشاملة باستخدام pg_dump وأرشفة سجلات WAL لتحقيق الاسترجاع لأي لحظة زمنية سابقة (Point-In-Time Recovery: PITR).

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution

1
تفعيل سياسات الـ RLS

ربط الجداول بسياسات أمان تعتمد على معرف المستخدم الحالي (current_setting('app.current_user_id')).

2
النسخ المنطقي بـ pg_dump

تصدير هياكل البيانات والجداول في أرشيف مضغوط متناسق دون قفل عمليات القراءة والكتابة.

3
الاسترجاع الزمني التام (PITR)

إعادة تشغيل سجلات الـ WAL للرجوع بالبيانات إلى الثانية التي سبقت حدوث الخطأ البشري مباشرة.

تحدي التوقع قبل التشغيل · Predict Before You Run

🤔 سؤال تحدي المهندسين:

لماذا يعتبر الـ Point-in-Time Recovery (PITR) منقذاً للحياة في حالات حذف الجداول بالخطأ (DROP TABLE) مقارنة بالنسخ الاحتياطي اليومي؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

لأن النسخ اليومي يفقد جميع بيانات اليوم حتى لحظة الحذف، بينما الـ PITR يعيد تشغيل سجلات الـ WAL حتى الدقيقة 14:29:59 (قبل تنفيذ أمر DROP TABLE بالثانية 14:30:00) دون فقدان أي معاملة سابقة.

تشريح الكود سطراً بسطر · Code Anatomy

1: ALTER TABLE invoices ENABLE ROW LEVEL SECURITY; // تفعيل أمان مستوى الصف
2: CREATE POLICY invoice_owner_policy ON invoices  // إنشاء سياسة الأمان
3:   FOR ALL USING (owner_id = current_setting('app.user_id')::uuid); // حصر الوصول للمالك فقط

معرض الأخطاء الشائعة والحل النموذجي · Mistakes Gallery

❌ الكود الخاطئ المسبب للكوارث (Anti-Pattern)
pg_dump -U postgres dbname > backup.sql /* ملف نصي ضخم غير مضغوط وبطيء في الاسترجاع */
✅ الحل الهندسي الصحيح (Best Practice)
pg_dump -Fc -Z 9 -U postgres dbname > backup.dump /* أرشيف ثنائي مخصص مضغوط فائق السرعة */

التشخيص الهندسي: النسخ النصي العادي يستهلك مساحة ضخمة ولا يدعم الاسترجاع المتوازي (Parallel Restore عبر pg_restore -j 4).

💬 سؤال إنترفيو للمهندسين الكبار (Senior Interview Q&A): ما هي معمارية الـ Write-Ahead Logging (WAL) وفيمَ تستخدم في PostgreSQL؟

الـ WAL هي سجل متسلسل غير قابل للتعديل (Append-Only Log) على القرص تُسجل فيه كل التعديلات قبل كتابتها في صفحات البيانات الفعلية؛ تضمن استرجاع البيانات الفوري عند انقطاع الكهرباء (Crash Recovery) وتُستخدم في مزامنة الـ Replication والاسترجاع الزمني (PITR).
