السياق والمشكلة الهندسية الواقعية

تشبيه الخزنة البنكية الحصينة وسجل المعاملات المزدوج · The Bank Vault & Ledger

تخيل إنك بتعمل عملية تحويل بنكي بمبلغ 10 آلاف جنيه من حساب أحمد لحساب سارة.. العملية دي محتاجة خطوتين: خصم 10 آلاف من أحمد، وإيداع 10 آلاف في حساب سارة.
لو السيستم خصم الفلوس من أحمد وفجأة الكهرباء قطعت عن السيرفر قبل ما يودع في حساب سارة.. الفلوس هتطير في الهواء ويحصل خراب بيوت!
هنا بقى بتظهر قوة ضمانات ACID في PostgreSQL:
- الذرية (Atomicity): المعاملة إما تكتمل الخطوتين بنجاح 100%، أو يتم التراجع عنها فوراً وكأن شيئاً لم يكن (Rollback)!
- الاستمرارية (Durability): المعاملة بتتسجل في سجل حديدي فوري على القرص اسمه (WAL Log)، فلو السيرفر اتحرق وولع، أول ما يشتغل تاني بيقرأ السجل ويسترجع كل قرش في مكانه المضبوط!

حروف كلمة ACID الأربعة باللغة الهندسية

1. Atomicity (الذرية): الكل أو لا شيء (All or Nothing).
2. Consistency (الاتساق): لا يمكن إدخال بيانات تكسر القيود (Foreign Keys, NOT NULL, CHECK constraints).
3. Isolation (العزل): العمليات المتزامنة لا ترى بيانات غير مكتملة لعمليات أخرى (تمنع Dirty Reads).
4. Durability (الديمومة): بمجرد كتابة COMMIT، التغيير دائم ومحفوظ على القرص حتى عند انقطاع الطاقة.

5. تشريح معاملة SQL ذرية متكاملة · Code Anatomy

1: BEGIN TRANSACTION; 2: UPDATE accounts SET balance = balance - 500 WHERE id = 1 AND balance >= 500; 3: UPDATE accounts SET balance = balance + 500 WHERE id = 2; 4: INSERT INTO audit_logs (from_id, to_id, amount) VALUES (1, 2, 500); 5: COMMIT;

السطر 1: بدء سياق المعاملة الذرية (Transaction Scope).

السطر 2: إضافة شرط balance >= 500 لمنع الوصول لرصيد سالب وضمان الاتساق.

السطر 5: تثبيت الخطوات الثلاث معاً في سجل القرص (Commit).

7. أخطاء شائعة وفخاخ يقع فيها الجميع · Common Pitfalls

توليد جمل SQL عبر دمج النصوص المباشر (SQL Injection Vulnerability)
// ❌ كارثة أمنية: يتيح للمخترق حذف قاعدة البيانات بالكامل!
db.query(`SELECT * FROM users WHERE email = '${email}'`);
// ✅ سليم: استخدام الاستعلامات المجهزة المعتمدة على المعاملات (Parameterized Queries)
db.query('SELECT * FROM users WHERE email = $1', [email]);

التشخيص الهندسي: الاستعلامات المجهزة تفصل كود الـ SQL عن بيانات المستخدم، وتمنع تفسير مدخلات المستخدم كأوامر برمجية.

سؤال مقابلات شهير: إيه الفرق بين EXPLAIN و EXPLAIN ANALYZE في PostgreSQL؟

الإجابة الهندسية:
- EXPLAIN: يوضح خطة التنفيذ المتوقعة (Estimated Cost & Rows) بناءً على إحصائيات المخطط دون تشغيل الاستعلام فعلياً.
- EXPLAIN ANALYZE: يقوم بتشغيل الاستعلام فعلياً ويقيس زمن التنفيذ الحقيقي بالميلي ثانية (Actual Time & Loops) وعدد الصفحات المقروءة من الذاكرة والقرص، وهو الأداة الأساسية لكشف بطء الاستعلامات في الإنتاج!
