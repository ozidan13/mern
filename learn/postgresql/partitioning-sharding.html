Declarative Table Partitioning: Range, List, Hash & Citus Distributed Sharding

تجزئة الجداول التصريحية (Partitioning): النطاقات، القوائم وتوزيع البيانات العملاقة بـ Citus

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم معمارية التجزئة التصريحية للجداول (Declarative Table Partitioning) وكيف تقسم الجداول الضخمة إلى جداول فرعية فيزيائية.
  • تطبيق استراتيجيات التجزئة الثلاث: تجزئة النطاقات (Range Partitioning)، القوائم (List Partitioning)، والتجزئة (Hash Partitioning).
  • فهم ميزة استبعاد الأقسام (Partition Pruning) وكيف يتجاهل المحرك قراءة 95% من الجداول الفرعية.
  • التوسع الأفقي العملاق عبر عدة خوادم باستخدام امتداد Citus Distributed PostgreSQL.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

عندما يصل جدول الطلبات أو جدول سجلات الـ Audit Logs إلى 100 مليون صف، يبدأ أداء الفهارس والاستعلامات بالتدهور: حجم فهرس B-Tree يتجاوز حجم الـ RAM، وعمليات الصيانة مثل VACUUM وإعادة بناء الفهارس تستغرق ساعات طويلة! الحل المعماري القياسي في PostgreSQL هو **تجزئة الجداول التصريحية (Declarative Table Partitioning)**. يتيح لك تقسيم الجدول العملاق إلى جداول فيزيائية أصغر (Partitions)، مثل إنشاء جدول فرعي لكل شهر (orders_2026_01, orders_2026_02...). التطبيق يتعامل مع جدول واحد رئيسي كالمعتاد، ولكن عندما ينفذ استعلاماً: SELECT * FROM orders WHERE ordered_at >= '2026-08-01' يقوم محرك الاستعلامات بميزة خارقة اسمها **Partition Pruning**: يتجاهل المحرك فوراً قراءة جداول باقي الشهور الـ 11، ويقرأ حصراً جدول شهر أغسطس، مما يقلل زمن الاستعلام بنسبة 90% ويوفر الذاكرة! في هذا الدرس، هنتعلم إزاي نبني جداول مجزأة ذاتية الإدارة، وهنتعرف على امتداد **Citus** لتوزيع الجداول عبر خوادم متعددة.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

إنشاء الجدول الأب بـ PARTITION BY RANGE

تعريف بنية الجدول وتحديد مفتاح التجزئة (مثل حقل التاريخ created_at) ليكون أساس توزيع البيانات.

02

إنشاء الجداول الفرعية (Child Partitions)

إنشاء جداول لكل شهر FOR VALUES FROM ('2026-08-01') TO ('2026-09-01') مع فهارس محلية مستقلة.

03

استبعاد الأقسام الذكي بـ Partition Pruning

يقوم مفسر الاستعلامات بفحص شرط WHERE واستبعاد قراءة الأقسام غير المعنية من خطة التنفيذ تماماً.

04

الحذف والأرشفة الفورية بـ DROP PARTITION

بدلاً من تشغيل DELETE البطيء لحذف بيانات قديمة، نقوم بفصل الجدول بـ DETACH PARTITION وحذفه في 1ms وبدون أي Lock.

05

التوزيع الأفقي بـ Citus Sharding Extension

تحويل PostgreSQL إلى قاعدة بيانات موزعة عملاقة تنشر الجداول عبر 100 سيرفر بـ create_distributed_table().

🤔 سؤال تحدي كبار المهندسين:

لماذا يعتبر حذف البيانات القديمة عبر ALTER TABLE ... DETACH PARTITION ثم DROP TABLE أسرع بآلاف المرات من كتابة DELETE FROM table WHERE date < ...؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

أمر DELETE العادي يقوم بمسح كل صف على حدة، وتوليد سجلات Oplog/WAL لكل عملية، وتحديث الفهارس، وإنشاء Dead Tuples تتطلب VACUUM لاحقاً (عملية مكلفة جداً). أما DETACH و DROP فيقوم ببساطة بقطع مؤشر الجدول الفرعي وحذف الملف الفيزيائي من القرص الصلب في خطوة واحدة على مستوى نظام التشغيل (Metadata-only drop) في أجزاء من الميلي ثانية وبدون أي استهلاك للـ CPU.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

-- إنشاء جدول مبيعات مجزأ حسب القوائم (List Partitioning) // تجزئة حسب الدول
CREATE TABLE regional_sales (                        // الجدول الرئيسي
  id UUID DEFAULT gen_random_uuid(),                 // معرف البيع
  country_code VARCHAR(2) NOT NULL,                  // مفتاح التجزئة
  amount NUMERIC(10, 2) NOT NULL                     // المبلغ
) PARTITION BY LIST (country_code);                  // تحديد نمط List
CREATE TABLE sales_mena PARTITION OF regional_sales FOR VALUES IN ('EG', 'SA', 'AE'); // قسم الشرق الأوسط
CREATE TABLE sales_eu PARTITION OF regional_sales FOR VALUES IN ('DE', 'FR', 'UK'); // قسم أوروبا

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: عدم تضمين مفتاح التجزئة داخل الـ PRIMARY KEY
CREATE TABLE sensor_data (
  id UUID PRIMARY KEY, // خطأ: بوستجريس ترفض إنشاء Primary Key لا يحتوي على مفتاح التجزئة!
  logged_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (logged_at);
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: تضمين مفتاح التجزئة في المفتاح الأساسي المركب
CREATE TABLE sensor_data (
  id UUID NOT NULL,
  logged_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, logged_at) // مفتاح مركب سليم
) PARTITION BY RANGE (logged_at);

التشخيص الهندسي: تفرض قواعد PostgreSQL تضمين عمود التجزئة في المفتاح الأساسي لضمان التحقق من الفرادة محلياً داخل كل قسم.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تدير إنشاء الأقسام المستقبلية تلقائياً (Automated Partition Management) لجدول زمني ينمو يومياً دون أي تدخل بشري؟

نستخدم أداة pg_partman (PostgreSQL Partition Manager Extension) أو نبني Trigger / Cron Job بـ pg_cron: نقوم بتكوين pg_partman.create_parent('public.orders', 'created_at', 'native', 'monthly') وضبط premake: 3. تقوم الأداة تلقائياً بإنشاء أقسام الأشهر الثلاثة القادمة مسبقاً في الخلفية، وفصل وأرشفة الأقسام القديمة تلقائياً إلى S3 أو جداول باردة بعد انقضاء سنة، محققة أتمتة كاملة بنسبة 100% لإدارة البيانات الضخمة.
