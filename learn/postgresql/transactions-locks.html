ACID Isolation Levels & Concurrency Locks: MVCC, Row Locks & Deadlock Prevention

مستويات عزل ACID وأقفال التزامن: معمارية MVCC، أقفال الصفوف ومنع الـ Deadlocks

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم معمارية التحكم متعدد الإصدارات في التزامن (MVCC) وكيف تضمن "القراءات لا تحظر الكتابة والكتابة لا تحظر القراءة".
  • تشريح مستويات عزل المعاملات الأربعة: Read Committed, Repeatable Read, و Serializable.
  • استخدام أقفال الصفوف الصريحة (Explicit Row Locking: SELECT ... FOR UPDATE / FOR SHARE).
  • فهم أسباب حدوث أقفال الموت (Deadlocks) وتطبيق استراتيجيات الترتيب الحتمي للوقاية منها.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في خادم قاعدة بيانات يعالج آلاف المعاملات في الثانية، تخيل المشهد التالي: مستخدمان يحاولان حجز آخر مقعد متبقي في طائرة في نفس الميلي ثانية: 1. المعاملة A تقرأ المقعد وتجده شاغراً (available = true). 2. المعاملة B تقرأ نفس المقعد وتجده شاغراً أيضاً! 3. المعاملة A تحجز المقعد وتدفع. 4. المعاملة B تحجز نفس المقعد وتدفع أيضاً (Double Booking Disaster)! ما لم تكن تملك فهماً عميقاً لـ **مستويات عزل المعاملات (ACID Isolation Levels)** و **أقفال الصفوف (SELECT ... FOR UPDATE)**، فإن بياناتك معرضة للفساد المالي. تتميز بوستجريس بمحرك **MVCC (Multi-Version Concurrency Control)** الأسطوري: عند تعديل صف، لا تقوم بقفله وحظر القراء؛ بل تنشئ نسخة جديدة من الصف (Tuple) مع الحفاظ على النسخة القديمة للقراء، محققة أقصى درجات التزامن والسرعة. في هذا الدرس، هنفكك أعماق محرك MVCC، وهنتعلم إزاي نقفل الصفوف الحرجة بأمان لمنع الـ **Deadlocks**.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

معمارية الـ MVCC وحقول xmin و xmax الخفية

كل صف في بوستجريس يحمل رقم معاملة الإنشاء (xmin) ومعاملة الحذف/التعديل (xmax) لتحديد رؤية الصف لكل معاملة.

02

مستوى العزل الافتراضي (Read Committed)

المعاملة ترى فقط البيانات التي تم تثبيتها (Committed) قبل بداية الاستعلام الحالي، وتمنع قراءة البيانات القذرة (Dirty Reads).

03

مستوى القراءات المتكررة (Repeatable Read)

المعاملة ترى لقطة زمنية ثابتة للبيانات منذ بداية المعاملة وتمنع ظاهرة القراءات غير المتكررة (Non-Repeatable Reads).

04

القفل التشاؤمي الصارم بـ SELECT FOR UPDATE

قفل الصف المختار ومنع أي معاملات أخرى من تعديله أو حجزه حتى تكتمل المعاملة الحالية بـ COMMIT.

05

الوقاية من الـ Deadlocks بالترتيب الحتمي

قفل الموارد دائماً بنفس الترتيب المنطقي الصارم (مثل الفرز بـ ID التصاعدي) لضمان عدم حدوث تعليق متبادل بين المعاملات.

ما هو الـ Deadlock وكيف يكتشفه محرك PostgreSQL ويقوم بحله تلقائياً؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

يحدث الـ Deadlock عندما تقفل المعاملة A الصف 1 وتطلب قفل الصف 2، بينما تقفل المعاملة B الصف 2 وتطلب قفل الصف 1 في نفس الوقت؛ فينتظر كل منهما الآخر للأبد! يمتلك PostgreSQL خيط فحص داخلي (Deadlock Detector) يستيقظ بعد مهلة deadlock_timeout (افتراضياً 1 ثانية)، وعند اكتشاف حلقة الانتظار المتبادلة، يقوم فوراً بإنهاء إحدى المعاملتين قسراً وإرجاع خطأ: ERROR: deadlock detected ليسمح للمعاملة الأخرى بالمرور.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;    // بدء المعاملة مع تحديد مستوى العزل
SELECT id, balance FROM wallets                      // استعلام قراءة الرصيد
WHERE user_id = '9921c5f8-8a8b-4c5e-8b1e-2c9e8f1a2b3c' // تحديد الحساب
FOR UPDATE; -- 🔒 فرض قفل حصري على الصف لمنع التعديلات المتزامنة // قفل الصف التشاؤمي
UPDATE wallets SET balance = balance - 100           // تعديل الرصيد بأمان
WHERE user_id = '9921c5f8-8a8b-4c5e-8b1e-2c9e8f1a2b3c'; // تطبيق التعديل
COMMIT; -- تحرير القفل وتثبيت التعديل                // تثبيت المعاملة

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع مسبب للحجز المزدوج: فحص بدون قفل
const seat = await db.query("SELECT * FROM seats WHERE id = $1 AND booked = false", [id]);
if (seat.rows.length > 0) {
  // لو وصل طلبان هنا معاً، سيقومان بالحجز مرتين لنفس المقعد!
  await db.query("UPDATE seats SET booked = true WHERE id = $1", [id]);
}
✅ الحل الهندسي القياسي (Best Practice)
// الحل الهندسي: استخدام SELECT ... FOR UPDATE
const seat = await db.query("SELECT * FROM seats WHERE id = $1 AND booked = false FOR UPDATE", [id]);
if (seat.rows.length > 0) {
  await db.query("UPDATE seats SET booked = true WHERE id = $1", [id]);
}

التشخيص الهندسي: الفحص بدون قفل يفتح نافذة سباق للعمليات المتزامنة، بينما FOR UPDATE يقفل الصف ويجبر الطلب الثاني على الانتظار حتى اكتمال الأول.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: ما هو دور عملية VACUUM و AUTOVACUUM في محرك PostgreSQL ولماذا يؤدي تعطيلها إلى تضخم حجم الجداول (Table Bloat) وبطء الاستعلامات؟

بسبب معمارية MVCC، عندما تقوم بتعديل أو حذف صف، لا يقوم بوستجريس بحذفه من القرص فوراً؛ بل يضع علامة عليه كـ Dead Tuple ليظل مرئياً للمعاملات الأقدم الجارية. عملية VACUUM / AUTOVACUUM هي "مجمع القمامة" الخاص بقاعدة البيانات: تقوم بالمسح الدوري للقرص لتحديد الـ Dead Tuples وإعادة تعليم مساحتها في خريطة المساحات الفارغة (Free Space Map - FSM) لتكون قابلة لإعادة الاستخدام في عمليات INSERT الجديدة. إذا تم تعطيل AutoVacuum، تستمر الصفوف الميتة في التراكم (Table Bloat)، مما يضاعف حجم الجداول على القرص ويجبر المحرك على قراءة ملايين الصفوف الميتة في كل استعلام مسبباً بطئاً كارثياً.
