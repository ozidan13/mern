Request-Response Lifecycle: Headers, Cookies, Streams & Content Negotiation

دورة حياة الطلب والاستجابة: الرؤوس، الكوكيز، التدفقات والتفاوض على المحتوى (Content Negotiation)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • تتبع الرحلة الكاملة لطلب HTTP منذ لحظة وصوله وحتى إرسال بايتات الرد وإغلاق الاتصال.
  • التحكم في رؤوس الأمان (Security Headers) ورؤوس الكاش (Cache-Control, ETag, 304 Not Modified).
  • إدارة ملفات تعريف الارتباط الآمنة (Secure Cookies) بخصائص HttpOnly و SameSite و Secure.
  • تطبيق التفاوض على المحتوى (Content Negotiation) عبر req.accepts() لدعم JSON و XML و CSV.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

الكثير من المطورين يعاملون إكسبريس كصندوق أسود: يكتب app.get('/data', (req, res) => res.json(data)) ويفترض أن السحر ينتهي هنا. لكن في الأنظمة الإنتاجية الكبرى، دورة حياة الطلب هي سلسلة دقيقة من المراحل: 1. مرحلة قراءة الرؤوس والتحقق من التشفير والـ Content-Type. 2. مرحلة التفاوض على المحتوى (Content Negotiation): هل يطلب العميل بيانات بصيغة JSON أم صفحة HTML أم ملف CSV؟ 3. مرحلة الكوكيز والجلسات: هل الكوكيز محمية بـ HttpOnly لمنع سرقتها عبر ثغرات XSS، ومضبوطة بـ SameSite=Strict لمنع هجمات CSRF؟ 4. مرحلة التحقق من الكاش عبر الـ ETag: لو لم تتغير البيانات، لماذا نرسل 500KB عبر الشبكة بينما يمكننا إرجاع كود 304 Not Modified في 0 بايت؟ في هذا الدرس، هنفكك دورة حياة الطلب والاستجابة بالكامل، وهنتعلم إزاي نتحكم في كل بايت يخرج من الخادم.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

استقبال وفك تغليف الرؤوس (Headers Parsing)

قراءة الرؤوس القياسية عبر req.get("Authorization") والتعامل مع حالات الأحرف غير الحساسة (Case-Insensitive).

02

التفاوض على المحتوى عبر req.accepts()

فحص رأس Accept وإرجاع التنسيق المفضل للعميل (JSON/XML/HTML) تلقائياً.

03

تعيين الكوكيز المؤمنة (HttpOnly, Secure, SameSite)

استخدام res.cookie() مع تفعيل HttpOnly لمنع وصول JavaScript للكوكيز و SameSite=Strict لمنع الـ CSRF.

04

إدارة الكاش الذكي بـ ETag و 304 Not Modified

إكسبريس تولد بصمة ETag تلقائياً وتفحص If-None-Match لإرجاع 304 بدون إرسال جسم البيانات إذا لم تتغير.

05

التدفق اللاتزامني وتفريغ الاستجابة (Stream Piping)

إرسال الملفات والتقارير الضخمة بـ stream.pipe(res) لمنع تراكم الذاكرة وإغلاق الاتصال بنظافة.

🤔 سؤال تحدي كبار المهندسين:

لماذا يعتبر تخزين رموز المصادقة (JWT) في HttpOnly Cookies أكثر أماناً بمراحل من تخزينها في localStorage داخل المتصفح؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

البيانات المخزنة في localStorage يمكن قراءتها وسرقتها بواسطة أي كود جافاسكريبت يعمل في الصفحة (مما يجعلها عرضة للسرقة فوراً عند حدوث أي ثغرة XSS). أما الـ HttpOnly Cookies، فإن المتصفح يمنع كود JavaScript تماماً من قراءتها (document.cookie لن يعيدها)، ويرسلها المتصفح تلقائياً ومباشرة مع طلبات الـ HTTP إلى الخادم بأمان تام.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

res.cookie("token", jwtToken, {                      // تعيين كوكيز المصادقة
  httpOnly: true, // حماية من هجمات XSS              // منع قراءة الكوكيز عبر JavaScript
  secure: process.env.NODE_ENV === "production",     // الإرسال عبر اتصالات HTTPS المشفرة فقط
  sameSite: "strict", // حماية من هجمات CSRF         // حظر إرسال الكوكيز في الطلبات العابرة للمواقع
  maxAge: 1000 * 60 * 60 * 24 * 7 // 7 أيام          // تحديد فترة صلاحية الكوكيز
});                                                  // نهاية إعدادات الكوكيز

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ أمني فادح: تعيين كوكيز حساسة بدون حماية HttpOnly
res.cookie("sessionId", id); // يمكن سرقتها بسهولة عبر كود XSS خبيث!
✅ الحل الهندسي القياسي (Best Practice)
// الحل الأمني المعتمد
res.cookie("sessionId", id, { httpOnly: true, secure: true, sameSite: "lax" });

التشخيص الهندسي: الكوكيز غير المحمية بـ HttpOnly تكون مكشوفة لأي سكربت خبيث في الصفحة، مما يتيح للمهاجمين انتحال شخصية المستخدمين.
