Body Parsing, Data Validation with Zod & Payload Size Defense

تحليل جسم الطلب (Body Parsing)، فحص المدخلات بـ Zod ومكافحة هجمات تضخيم البيانات

⏱️ 30 دقيقة تعليمية
🎯 المستوى: تأسيسي متقدم
⚡ الإصدار: Express 5.2 & Zod v3
📐 النمط: Data Validation & Defensive Parsing

🎯 مخرجات التعلم وأهداف الدرس

  • ✓ فهم كيفية عمل وسائط express.json() و express.urlencoded() وكيف تحول التدفقات إلى كائنات.
  • ✓ حماية الخادم من هجمات حرمان الخدمة (DoS) بتحديد سقف صارم لحجم البيانات limit: "100kb".
  • ✓ بناء طبقة تحقق صارمة من النوع (Type-Safe Validation Pipeline) باستخدام مكتبة Zod.
  • ✓ توليد رسائل خطأ دقيقة ومفصلة للمدخلات غير الصالحة وتطهير الحقول الزائدة (Stripping Unknown Keys).

الفكرة الأساسية وسياق العالم الحقيقي

لماذا نحتاج هذا المفهوم وكيف يحل مشاكل الإنتاج المعقدة؟

في خوادم الـ REST API، القول المأثور الأهم في الأمن السيبراني هو: **"لا تثق أبداً في مدخلات المستخدم (Never Trust User Input)"**! لو لم تحدد سقفاً لحجم جسم الطلب في إكسبريس، يستطيع أي مهاجم إرسال طلب POST بحجم 100 ميجابايت يحتوي على نص JSON ضخم، مما يملأ ذاكرة الـ RAM ويجمد الخادم في محاولة فك التشفير! والأخطر من ذلك هو تمرير حقول غير مفحوصة مباشرة لقاعدة البيانات: تخيل مستخدم يرسل في طلب تعديل حسابه: { "role": "superadmin", "balance": 999999 }! لو كان كودك يفعل User.update(req.body) بدون فحص صارم، فقد تم اختراق موقعك بالكامل (Mass Assignment Vulnerability). الحل المعماري القياسي في بيئات TypeScript و JavaScript الحديثة هو دمج إكسبريس مع مكتبة **Zod**. في هذا الدرس، هنتعلم إزاي نبني وسيط تحقق تلقائي يفحص المدخلات قبل وصولها للمسار، يطهر الحقول الخبيثة، ويضمن Type Safety كامل في التطبيق.

📖 تشبيه واقعي من بيئة العمل الهندسية

ثغرة Mass Assignment تحدث عندما يقوم المطور بتمرير req.body مباشرة إلى دالة التحديث في الداتابيز User.update(req.body). يستطيع المهاجم إضافة حقول مثل isAdmin: true أو verified: true إلى جسم الطلب. تحمي Zod التطبيق لأنها تقوم تلقائياً بـ "Strip" وحذف أي حقول لم يتم التصريح عنها صراحة في الـ Schema، وتُرجع في result.data الحقول المصرح بها فقط.

الميكانيكا العميقة: كيف يعمل خطوة بخطوة؟

تشريح تفصيلي لآلية العمل ومراحل التنفيذ داخل المحرك

01

تحديد حدود الحجم الآمنة (express.json with limit)

تكوين app.use(express.json({ limit: "50kb" })) لحظر الطلبات المتضخمة فوراً قبل استهلاك موارد الذاكرة.

02

بناء مخططات الفحص بلغة Zod Schema

تعريف القواعد الصارمة للحقول (مثل البريد الإلكتروني، قوة كلمة المرور، ونطاقات الأرقام) بـ z.object().

03

بناء وسيط التحقق الشامل (Validate Middleware)

إنشاء وسيط يستقبل الـ Schema وينفذ schema.safeParseAsync(req.body) لتمرير البيانات النظيفة فقط.

04

تطهير الحقول الزائدة غير المصرح بها (Key Stripping)

مكتبة Zod تتجاهل وتحذف تلقائياً أي حقول إضافية غير مذكورة في الـ Schema لحماية قاعدة البيانات من Mass Assignment.

05

تنسيق رسائل الأخطاء المعيارية (Zod Error Formatting)

تحويل أخطاء التحقق إلى مصفوفة واضحة { field: "email", message: "Invalid format" } بكود 400 Bad Request.

تشريح الكود سطر بسطر (Code Anatomy)

فهم وظيفة كل سطر برمجياً ومعمارياً

CODE SNIPPET الشرح الهندسي والدلالة
import { z } from "zod"; استيراد مكتبة الفحص Zod
export const registerSchema = z.object({ تعريف مخطط تسجيل المستخدم
email: z.string().email("Invalid email format"), فحص البريد الإلكتروني
password: z.string().min(8, "Password must be at least 8 chars"), فحص طول كلمة المرور
age: z.number().int().min(18).optional(), حقل عمري اختياري
}); نهاية المخطط
export const validate = (schema) => async (req, res, next) => { وسيط الفحص التلقائي
const result = await schema.safeParseAsync(req.body); فحص البيانات بأمان
if (!result.success) return res.status(400).json({ errors: result.error.errors }); إرجاع كود 400 عند الخطأ
req.body = result.data; // استبدال الجسم بالبيانات المطهرة فقط حقن البيانات المطهرة
next(); تمرير الطلب للمسار
}; نهاية الوسيط

أخطاء الإنتاج القاتلة مقابل أفضل الممارسات

مقارنة بصرية واضحة بين الكود الكارثي والكود الهندسي المعتمد

🚨 الكود الخاطئ / Anti-Pattern 
// خطأ أمني كارثي: Mass Assignment مباشر في قاعدة البيانات
app.put("/users/:id", async (req, res) => {
  await User.update(req.params.id, req.body); // يتيح للمستخدم ترقية نفسه لـ admin وتعديل رصيده!
});
✨ الكود الهندسي المعتمد / Best Practice 
// الحل الهندسي: التحقق والتطهير بـ Zod قبل اللمس
app.put("/users/:id", validate(updateUserSchema), async (req, res) => {
  await User.update(req.params.id, req.body); // req.body يحتوي فقط على الحقول المسموح بتعديلها
});

ننشئ حزمة مشتركة في الـ Monorepo باسم @project/shared-schemas تحتوي على مخططات Zod (مثل UserRegisterSchema). في الباك إند: نستخدم الـ Schema للتحقق في الـ Middleware. في الفرونت إند: نستخرج الأنواع تلقائياً بـ type UserRegisterInput = z.infer<typeof UserRegisterSchema> ونربطها بنماذج React Hook Form عبر @hookform/resolvers/zod. هذا يضمن أن أي تعديل في قواعد البيانات أو الحقول ينعكس فورياً كأخطاء Compile-time في الفرونت إند والباك إند في نفس اللحظة.
