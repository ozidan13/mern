Middleware Architecture: Chain-of-Responsibility, Async Handlers & Next() Mechanics

معمارية البرمجيات الوسيطة (Middleware): نمط سلسلة المسؤولية، الدوال اللاتزامنية وميكانيكا next()

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم نمط سلسلة المسؤولية (Chain-of-Responsibility Pattern) وكيف يعالج خط الأنابيب (Pipeline) الطلبات.
  • تشريح سلوك دالة next() والفرق بين next()، next("route")، و next(err).
  • فهم ميزة المعالجة اللاتزامنية الأصلية في Express 5 (Native Async/Await بدون express-async-errors).
  • بناء وسائط مخصصة قابلة للتهيئة (Configurable Middleware Factories).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

الـ Middleware هو القلب النابض لإكسبريس: كل شيء من فحص المصادقة، تسجيل الطلبات (Logger)، ضغط البيانات (Compression)، وفحص الصلاحيات، هو عبارة عن برمجيات وسيطة تصطف في طابور متتابع لمعالجة الطلب. في Express 4 القديمة، كانت هناك مشكلة شهيرة تتسبب في تجميد السيرفر: لو حدث خطأ داخل دالة async (req, res, next)، كان الخطأ يسقط في الـ Unhandled Promise Rejection ويتجمد الطلب للأبد لأن إكسبريس 4 لم تكن تفهم الـ Promises! في **Express 5 الحديثة**، تم حل هذه المشكلة جذرياً: أصبح خط أنابيب الميدلوير يدعم الـ Promises أصلياً، وأي دالة async ترمي خطأ يتم التقاطه تلقائياً وتمريره لوسيط معالجة الأخطاء دون الحاجة لمكتبات مساعدة. في هذا الدرس، هنغوص في ميكانيكا عمل next()، وهنتعلم إزاي نبني Middleware Factories احترافية تدعم تمرير خيارات ديناميكية.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

طابور المعالجة التسلسلي (Middleware Stack)

تنفيذ الوسائط بالترتيب الدقيق لتسجيلها بـ app.use() حتى يقوم أحدها بإرسال الرد أو استدعاء next().

02

سلوكيات استدعاء next() الثلاثة

استدعاء next() يمرر للوسيط التالي؛ next("route") يتخطى باقي وسائط نفس المسار؛ next(err) يقفز مباشرة لوسيط معالجة الأخطاء.

03

الدعم اللاتزامني الأصلي في Express 5

الدوال اللاتزامنية async تلتقط الأخطاء المرفوضة (Rejected Promises) وتمررها تلقائياً لـ error handler دون كتابة try/catch يدوية.

04

مصانع الميدلوير المهيأة (Middleware Factories)

دوال تستقبل إعدادات وتُرجع دالة وسيطة مخصصة (req, res, next) مثل rateLimit({ max: 100 }).

05

حقن البيانات في سياق الطلب (Request Context Augmentation)

تخزين بيانات المستخدم والتحليلات في req.user و req.requestId لتكون متاحة لكافة المسارات اللاحقة.

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

استدعاء next() مرتين سيؤدي لتنفيذ المسارات اللاحقة مرتين لنفس الطلب الواحد! وإذا حاول المسار الثاني إرسال رد للمتصفح، سيرمي Node.js خطأ فورياً من نوع Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client. لتفادي ذلك، يجب دائماً كتابة return next() لإنهاء تنفيذ الدالة فوراً بعد تمرير الطلب.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

export const requireRole = (allowedRole) => {     // مصنع ميدلوير يستقبل الصلاحية المطلوبة
  return (req, res, next) => {                    // إرجاع الدالة الوسيطة الفعلية
    if (!req.user || req.user.role !== allowedRole) { // فحص الصلاحية
      return res.status(403).json({ error: "Forbidden: Insufficient privileges" }); // حظر الوصول
    }                                                // نهاية الفحص
    next(); // تمرير الطلب للمسار التالي             // تمرير سليم
  };                                                 // نهاية الدالة الوسيطة
};                                                   // نهاية المصنع

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: نسيان return عند استدعاء next() بعد إرسال الرد
if (!authenticated) {
  res.status(401).send("Unauthorized");
  next(); // خطأ: سيستمر الكود في التنفيذ ويرسل رداً ثانياً مسبباً ERR_HTTP_HEADERS_SENT!
}
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: استخدام return دائماً لقطع التنفيذ
if (!authenticated) {
  return res.status(401).send("Unauthorized");
}
next();

التشخيص الهندسي: استدعاء res.send أو res.json لا يوقف تنفيذ باقي أسطر الدالة تلقائياً؛ يجب استخدام return لضمان عدم تنفيذ الأكواد التالية.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تنفذ نمط Correlation ID (Request Tracing ID) باستخدام Middleware لتتبع مسار الطلب الواحد عبر عدة خدمات مايكروسيرفس وسجلات الـ Logs؟

ننشئ Request Tracing Middleware في بداية خط الأنابيب: 1. يفحص الرأس القادم req.get("x-correlation-id") || crypto.randomUUID(). 2. يحقن المعرف في كائن الطلب req.correlationId = id. 3. يضيف الرأس في الاستجابة res.setHeader("x-correlation-id", id). 4. يربط المعرف بنظام التسجيل (Winston / Pino) لطباعة الـ Correlation ID مع كل سطر Log خاص بهذا الطلب، مما يتيح للـ DevOps البحث عن معرّف الطلب في Grafana/Kibana وتتبع رحلته الكاملة عبر 10 مايكروسيرفس بسهولة.
