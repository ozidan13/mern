N-Tier Layered Architecture: Controllers, Services, Repositories & DTOs

المعمارية متعددة الطبقات (N-Tier): وحدات التحكم والخدمات والمستودعات والـ DTOs

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم حدود ومسؤوليات الطبقات الأربع الصارمة: Controller (HTTP Transport), Service (Business Logic), Repository (Data Access), DTO (Data Contract).
  • تطبيق مبدأ المسؤولية الفردية (Single Responsibility Principle) وفصل منطق الأعمال تماماً عن كائنات الـ HTTP (req / res).
  • بناء طبقة مستودعات البيانات (Repository Layer) لتسهيل تغيير محركات البيانات (Prisma / Mongoose / SQL) دون لمس منطق الأعمال.
  • كتابة اختبارات الوحدات (Unit Tests) المعزولة بنسبة 100% عبر عمل Mocking لطبقة الـ Repositories.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في المشاريع المبتدئة، تجد المطور يكتب كل شيء داخل دالة الموجه (Route Handler): يقوم بقراءة req.body، فحص المدخلات، الاتصال بقاعدة البيانات، حساب الضرائب، إرسال إيميل ترحيبي، وتنسيق رد الـ JSON في 300 سطر متداخل داخل نفس الملف (Fat Controllers)! هذا الكود يسمى في هندسة البرمجيات **Spaghetti Code**: - لو أردت كتابة Unit Test لحساب الضرائب، ستضطر لتشغيل خادم HTTP وهمي ومحاكاة طلب كامل! - لو طلبت الإدارة غداً إتاحة نفس الوظيفة عبر WebSocket أو عبر CLI Script أو Message Queue Worker، ستضطر لإعادة كتابة الكود من الصفر لأن منطق الأعمال محبوس داخل كائنات req و res الخاصة بـ Express! **المعمارية متعددة الطبقات (N-Tier Layered Architecture)** تحل هذه الفوضى بتقسيم النظام إلى 4 طبقات معزولة ذات تدفق أحادي الاتجاه: 1. **Controller Layer**: تتحدث HTTP فقط. 2. **Service Layer**: عقل النظام (Business Logic) النقي الخالي من أي تبعيات ويب. 3. **Repository Layer**: وسيط التحدث مع قواعد البيانات. 4. **DTO Layer**: عقود نقل البيانات والتحقق. في هذا الدرس التأسيسي لمسار هندسة النظم، هنبني تطبيقاُ معمارياً نظيفاً يعكس معايير الشركات العالمية.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

طبقة التحكم (Controller Layer: HTTP Only)

تستقبل كائن req، وتفحصه عبر DTO، وتمرر البيانات النظيفة للـ Service، وتحدد كود حالة الرد res.status(201).json().

02

طبقة الخدمات (Service Layer: Pure Business Logic)

تحتوي على كل الحسابات وقواعد الأعمال والتحقق المالي؛ لا تعرف أي شيء عن Express وتعمل كدوال TypeScript نقية.

03

طبقة المستودعات (Repository Layer: Data Access)

تتولى التحدث مع Prisma أو PostgreSQL؛ وتتيح تبديل قاعدة البيانات أو استبدالها بـ Mock في الاختبارات بسهولة.

04

كائنات نقل البيانات (Data Transfer Objects - DTOs)

عقود بيانية صارمة تحدد شكل المدخلات والمخرجات وتمنع تسريب الحقول الحساسة (مثل كلمات المرور) للمستخدم.

05

حقن التبعيات (Dependency Injection Pattern)

تمرير الـ Repository إلى الـ Service عبر الـ Constructor لتسهيل عزل الطبقات وتطبيق الـ Inversion of Control.

🤔 سؤال تحدي كبار المهندسين:

لماذا يعتبر تمرير كائني req و res إلى طبقة الـ Service خطأً معمارياً فادحاً (Architectural Smelling)?

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

لأن تمرير كائنات الـ HTTP يربط منطق الأعمال ببروتوكول Express حصراً (Tight Coupling). إذا أردت لاحقاً تشغيل نفس الخدمة عبر WebSocket أو داخل Background Worker أو استدعائها في Unit Test، ستضطر لاصطناع كائنات req/res وهمية! طبقة الـ Service يجب أن تستقبل وتُرجع كائنات جافاسكريبت نقية (Plain DTOs) مستقلة تماماً عن بروتوكولات النقل.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

// 1. Service Layer (Pure TypeScript)                // طبقة الأعمال النقية
export class OrderService {                          // فئة الخدمة
  constructor(private orderRepo: IOrderRepository, private paymentGateway: IPayment) {} // حقن التبعيات بالواجهات
  async placeOrder(dto: CreateOrderDTO): Promise<OrderResponseDTO> { // دالة استقبال DTO النقي
    const total = calculateTaxesAndDiscounts(dto.items); // Business calculation // حسابات منطق الأعمال
    await this.paymentGateway.charge(dto.paymentToken, total); // الدفع المالي
    return await this.orderRepo.save({ ...dto, total }); // الحفظ عبر المستودع
  }                                                  // نهاية دالة الأعمال
}                                                    // نهاية الفئة

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ معماري فادح: كتابة استعلامات الداتابيز ومنطق الأعمال في دالة Controller
app.post("/users", async (req, res) => {
  if (req.body.age < 18) return res.send("too young"); // Business Logic
  const user = await prisma.user.create({ data: req.body }); // Database Logic
  await sendEmail(user.email); // Side Effects
  res.json(user); // HTTP
});
✅ الحل الهندسي القياسي (Best Practice)
// الحل المعماري القياسي: توزيع المسؤوليات على الطبقات
export class UserController {
  async register(req: Request, res: Response) {
    const user = await this.userService.register(req.body);
    return res.status(201).json({ data: user });
  }
}

التشخيص الهندسي: حشو كل المسؤوليات في الـ Controller يمنع إعادة الاستخدام والاختبار، بينما فصل الطبقات يتيح صيانة كل جزء وتطويره بشكل مستقل.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تطبق نمط Dependency Inversion Principle (DIP) وحقن التبعيات (DI) في تطبيق Node.js بدون استخدام أطر عمل ضخمة مثل NestJS؟

نطبقه باستخدام Pure TypeScript Interfaces ومصانع الـ Containers (Pure DI / Manual Composition Root): 1. نعرف Interface مجردة: interface IUserRepository { findById(id: string): Promise; }. 2. نجعل UserService يعتمد حصراً على الـ Interface: constructor(private userRepo: IUserRepository). 3. في ملف التكوين الجذري (composition-root.ts)، ننشئ النسخ الحقيقية: const userRepo = new PrismaUserRepository(prisma); const userService = new UserService(userRepo); const userController = new UserController(userService). هذا يوفر فصلاً كاملاً للتبعيات ويسهل استبدال PrismaUserRepository بـ MockUserRepository في الاختبارات.
