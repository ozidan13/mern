Enterprise Auth Architecture: OAuth 2.1, OIDC, Session Rotation & SSO

معمارية التوثيق المتقدمة للمؤسسات: بروتوكول OAuth 2.1 وتسجيل الدخول الموحد (SSO)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم تدفق OAuth 2.1 Authorization Code Flow مع حماية PKCE الإلزامية.
  • التمييز بين ID Token (لإثبات الهوية) و Access Token (لصلاحيات الـ API).
  • بناء خادم توثيق موزع يعتمد على Redis لإبطال الجلسات الفوري (Session Invalidation).

المشكلة الهندسية والسياق الواقعي

رؤية الواقع العملي · Real-World Context & Mental Model

التوثيق في المنظومات الكبرى يتجاوز تسجيل الدخول بكلمة السر. بروتوكول OAuth 2.1 و OpenID Connect (OIDC) هو المعيار العالمي للتفويض والتوثيق الموحد (Single Sign-On: SSO مع Google و GitHub و Okta). فهم معمارية تدفق الـ PKCE (Proof Key for Code Exchange) وحماية الرموز المشفرة وتدوير الجلسات في Redis يضمن حماية المنظومة من أحدث ثغرات التفويض وسرقة الهويات.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution

1
توليد الـ PKCE Code Verifier & Challenge

إنشاء رمز سري عشوائي وتشفيره بـ SHA-256 لمنع اعتراض كود التفويض على المتصفح والموبايل.

2
التحقق وإصدار الرموز (OIDC Tokens)

الخادم يطابق الـ Verifier ويصدر ID Token (JWT) و Access Token.

3
الإبطال الفوري للجلسات (Redis Blocklist)

تسجيل الرموز المسروقة أو المنتهية في Redis لطرد المستخدم من كل الأجهزة فورياً.

تحدي التوقع قبل التشغيل · Predict Before You Run

🤔 سؤال تحدي المهندسين:

لماذا ألغى معيار OAuth 2.1 الحديث تدفق Implicit Flow وأوجب استخدام PKCE لجميع التطبيقات؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

لأن Implicit Flow كان يعيد الـ Access Token مباشرة في عنوان الـ URL (Hash Fragment) مما يعرضه للسرقة عبر سجلات المتصفح وثغرات Referrer Headers؛ تم استبداله بـ Authorization Code + PKCE المشفر.

تشريح الكود سطراً بسطر · Code Anatomy

1: // OpenID Connect Token Verification            // التحقق من رمز الهوية
2: const payload = await verifyGoogleIdToken(req.body.credential); // مطابقة توقيع جوجل الرسمي
3: const user = await findOrCreateUser({ email: payload.email }); // إنشاء أو جلب المستخدم
4: const sessionToken = issueAppSession(user);     // إصدار جلسة النظام الداخلية

معرض الأخطاء الشائعة والحل النموذجي · Mistakes Gallery

❌ الكود الخاطئ المسبب للكوارث (Anti-Pattern)
استخدام Access Token للتحقق من هوية المستخدم بدلاً من ID Token في OIDC
✅ الحل الهندسي الصحيح (Best Practice)
استخدام ID Token لمعرفة هوية المستخدم و Access Token للتفويض في الـ API

التشخيص الهندسي: الـ Access Token مصمم للـ Resource Server ولا يضمن هوية المستخدم للفرونت إند.

💬 سؤال إنترفيو للمهندسين الكبار (Senior Interview Q&A): كيف تنفذ ميزة "تسجيل الخروج من جميع الأجهزة" (Logout from all devices) مع رموز JWT عديمة الحالة (Stateless)?

نضيف حقلاً في جدول المستخدم يسمى `tokenVersion` (أو `jwtTimestamp`) ونضمن قيمته داخل حمولة الـ JWT؛ عندما يطلب المستخدم تسجيل الخروج من كل الأجهزة نقوم بزيادة `tokenVersion = tokenVersion + 1` في قاعدة البيانات؛ فيرفض وسيط التوثيق أي رمز يحمل إصداراً قديماً فوراً.
