Real-Time Architecture: WebSockets, Socket.io, SSE & Redis Pub/Sub Adapters

المشكلة الهندسية والسياق الواقعي

رؤية الواقع العملي · Real-World Context & Mental Model

في تطبيقات المحادثات الحية (Chat Systems)، التحديثات اللحظية للأسعار، والإشعارات، إرسال طلبات HTTP Polling متكررة كل ثانيتين يهلك السيرفر والبطارية وينقل 99% من البيانات الفارغة! بروتوكول WebSockets يفتح اتصال TCP ثنائي الاتجاه ودائم (Full-Duplex) بزمن انتقال شبه معدوم. ولكن عند توسيع السيرفر لعدة خوادم (Cluster)، يظهر التحدي الأكبر: كيف يرسل مستخدم في السيرفر A رسالة لمستخدم في السيرفر B؟ الحل هو Redis Pub/Sub Adapter.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution

1
مصافحة الـ HTTP Upgrade

الاتصال يبدأ كـ HTTP عادي ثم يطلب الترقية (101 Switching Protocols) لـ WebSocket TCP Stream.

2
نظام الغرف (Rooms & Namespaces)

تجميع المتصلين في غرف خاصة (مثل chat:room:101) لبث الرسائل للمعنيين فقط.

3
موزع Redis Pub/Sub

نقل الرسائل بين خوادم Node.js المختلفة عبر قنوات Redis لضمان وصول الرسالة لكل المشتركين.

تحدي التوقع قبل التشغيل · Predict Before You Run

🤔 سؤال تحدي المهندسين:

متى تفضل استخدام Server-Sent Events (SSE) على WebSockets في تطبيقات الإنتاج؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

نفضل SSE عندما يكون تدفق البيانات في اتجاه واحد فقط من السيرفر للعميل (One-Way Streaming مثل بث أسعار الأسهم، شاشات الـ Dashboard الحية، أو ردود الـ AI التوليدية Streaming LLM) لأنها تعمل فوق HTTP/2 القياسي وتدعم إعادة الاتصال التلقائي دون تعقيدات WebSockets.

معرض الأخطاء الشائعة والحل النموذجي · Mistakes Gallery

❌ الكود الخاطئ المسبب للكوارث (Anti-Pattern)
بث الرسائل الحية للعامة io.emit() بدلاً من حصرها في غرف الغرض io.to(roomId).emit()
✅ الحل الهندسي الصحيح (Best Practice)
استخدام Rooms لتوجيه الرسائل للمشاركين المعنيين حصراً
