Event-Driven Architecture: Event Sourcing, CQRS & Apache Kafka Stream Processing

المعمارية الموجهة بالأحداث (EDA): نمط Event Sourcing، فصل القراءة والكتابة (CQRS) وتدفقات Kafka

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم صلب المعمارية الموجهة بالأحداث (Event-Driven Architecture) ونمط الناشر/المشترك (Pub/Sub).
  • تشريح نمط استرجاع الأحداث (Event Sourcing): حفظ كل تغيير في النظام كحدث تاريخي غير قابل للتعديل (Immutable Append-Only Log).
  • تطبيق نمط فصل مسؤوليات الاستعلام والأوامر (Command Query Responsibility Segregation - CQRS).
  • فهم معمارية تدفقات البيانات الضخمة بـ Apache Kafka (Topics, Partitions, Consumer Groups, Offsets).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في قواعد البيانات التقليدية (CRUD)، عندما يقوم المستخدم بتعديل عنوانه 5 مرات، فإنك تقوم بعمل UPDATE لنفس الصف؛ فيختفي العنوان القديم وتبقى القيمة الأخيرة فقط! لو سألك المدقق المالي أو القانوني: "ماذا كان عنوان العميل يوم 15 يناير الماضي وقت إجراء المعاملة المشبوهة؟"، لن تستطيع الإجابة لأنك قمت بمسح التاريخ! في الأنظمة البنكية، أسواق الأسهم، وأنظمة التجارة الكبرى، يتم بناء الأنظمة بنمط **Event Sourcing**: - لا نقوم بحفظ "الحالة الحالية" (Current State)؛ بل نحفظ **سلسلة الأحداث التاريخية غير القابلة للتعديل (Immutable Event Log)**: AccountCreated -> FundsDeposited(100) -> FundsTransferred(40) -> AddressUpdated. - الحالة الحالية هي ببساطة ناتج إعادة تشغيل (Replaying) هذه الأحداث من البداية! وعند دمج Event Sourcing مع نمط **CQRS**، نقوم بفصل قاعدة بيانات الكتابة (المحسنة للكتابة السريعة بـ Kafka/EventStore) عن قواعد بيانات القراءة (المحسنة للبحث السريع بـ Elasticsearch و PostgreSQL Read Models). في هذا الدرس المتقدم، هنفكك المعمارية الموجهة بالأحداث، وهنتعلم أسرار **Apache Kafka**.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

سجل الأحداث غير القابل للتعديل (Append-Only Event Store)

تسجيل الأحداث كحقائق تاريخية ماضية (e.g. OrderPlaced, PaymentReceived) لا يمكن تعديلها أو حذفها نهائياً.

02

فصل القراءة عن الكتابة بـ CQRS Pattern

نموذج الأوامر (Commands) يركز على منطق الأعمال والكتابة؛ بينما نموذج الاستعلام (Queries) يقرأ من Read Projections محسنة وفائقة السرعة.

03

إعادة بناء الحالة بـ Event Replay

حساب الرصيد الحالي أو حالة الطلب عبر تجميع وتطبيق قائمة الأحداث التاريخية sequentially.

04

معمارية تدفقات Apache Kafka

توزيع الأحداث عبر Topics مقسمة إلى Partitions، ومعالجة الملايين من الرسائل بالتوازي عبر Consumer Groups مع تتبع الـ Offset.

05

لقطات الحالة المؤقتة (Snapshots Optimization)

أخذ لقطة لحالة الحساب كل 1000 حدث لمنع إعادة تشغيل ملايين الأحداث القديمة عند كل قراءة.

🤔 سؤال تحدي كبار المهندسين:

ما هي مشكلة الـ Eventual Consistency في نمط CQRS وكيف يتعامل معها تطبيق الواجهة الأمامية عند تحديث البيانات؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

في CQRS، بعد أن يرسل المستخدم أمر الكتابة ويتم حفظ الحدث في الـ Event Store، قد يستغرق مزامنة وتحديث نموذج القراءة (Read Model) بضعة ميلي ثوانٍ (Eventual Consistency Lag). إذا قام المستخدم بالتحويل لصفحة العرض فوراً، قد يرى بياناته القديمة! لحل ذلك في الفرونت إند: 1. نطبق Optimistic UI Updates في شاشة React لعرض التعديل فوراً. 2. نرسل إشعار WebSocket من السيرفر عند اكتمال تحديث الـ Read Model لإعادة مزامنة الشاشة بسلاسة.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

// CQRS Command Handler & Event Dispatcher       // معالج أوامر CQRS
export class PlaceOrderCommandHandler {              // فئة معالجة الأمر
  constructor(private eventStore: IEventStore, private kafkaProducer: IKafka) {} // حقن التبعيات
  async handle(command: PlaceOrderCommand): Promise<string> { // تنفيذ الأمر
    // 1. Validate Business Rules                    // فحص القواعد
    if (command.items.length === 0) throw new Error("Order cannot be empty"); // تحقق الأعمال
    // 2. Create Immutable Domain Event              // إنشاء الحدث التاريخي
    const orderEvent = new OrderPlacedEvent(command.orderId, command.userId, command.items); // كائن الحدث
    // 3. Persist Event to Append-Only Store and Broadcast to Kafka // الحفظ والبث
    await this.eventStore.append(orderEvent);        // حفظ في السجل
    await this.kafkaProducer.send("order-events", orderEvent); // Asynchronous Broadcast // بث في Kafka
    return command.orderId;                          // إرجاع المعرف
  }                                                  // نهاية المعالج
}                                                    // نهاية الفئة

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تحل مشكلة الـ Dual-Write Problem عند الحاجة لتعديل قاعدة بيانات PostgreSQL وبث رسالة لـ Apache Kafka في نفس الوقت لمنع فقدان البيانات؟

نطبق نمط Transactional Outbox Pattern: 1. داخل نفس معاملة PostgreSQL ACID: نقوم بتعديل جدول الأعمال (e.g. orders) وإدخال سجل جديد في جدول مخصص اسمه outbox_table يحمل بيانات الرسالة. 2. بما أن العمليتين في معاملة SQL واحدة، فإما أن تنجحا معاً أو تفشلا معاً. 3. نستخدم أداة Change Data Capture (CDC مثل Debezium) أو Worker منفصل يقوم بقراءة جدول الـ outbox عبر PostgreSQL Write-Ahead Log (WAL) وبث الرسائل إلى Apache Kafka فورياً وبضمان تسليم 100% (Zero Message Loss).
