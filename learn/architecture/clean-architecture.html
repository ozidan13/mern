Clean Architecture & Hexagonal (Ports and Adapters): Domain-Centric Design

العمارة النظيفة (Clean Architecture) والمعمارية السداسية: التصميم المتمحور حول النطاق (Ports & Adapters)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم دوائر العمارة النظيفة الأربع (Entities, Use Cases, Interface Adapters, Frameworks/Drivers).
  • تطبيق قاعدة الاعتمادية الصارمة (The Dependency Rule: الاعتماديات تتجه للداخل دائماً نحو Domain Core).
  • بناء المنافذ والمحولات (Ports and Adapters): قيادة النطاق عبر Inbound Ports والتكامل مع الخدمات بـ Outbound Ports.
  • عزل منطق الأعمال تماماً عن قواعد البيانات وأطر العمل الخارجية (Database is an Implementation Detail).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في معظم المشاريع، تبدأ كتابة الكود بتصميم جداول قاعدة البيانات! هذا يجعل قاعدة البيانات هي المركز، ويصبح كل كود التطبيق معتمداً ومرتهناً لأطر العمل الخارجية (Framework-Centric Design). عندما أصدر **Uncle Bob (Robert C. Martin)** مفهوم **Clean Architecture** ومفهوم **Hexagonal Architecture (المعمارية السداسية)** لأليستير كوكبيرن، قاما بقلب الهرم بالكامل: - **"قاعدة البيانات هي مجرد تفصيلة تقنية هامشية (The Database is a Detail)"**! - **"إطار العمل Express أو Fastify هو مجرد تفصيلة خارجية (The Web Framework is a Detail)"**! قلب النظام الحقيقي هو **Entities** و **Use Cases** (منطق الأعمال النقي المجرد). تخيل أنك تستطيع تغيير قاعدة البيانات من PostgreSQL إلى MongoDB، أو تغيير واجهة الـ API من REST إلى GraphQL أو gRPC، **دون تعديل سطر واحد داخل Use Cases أو منطق الأعمال**! في هذا الدرس، هنتعلم إزاي نبني معمارية Ports and Adapters منيعة، وهنتعلم القواعد الصارمة لـ **The Dependency Rule**.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

قاعدة الاعتمادية الصارمة (The Dependency Rule)

الأكواد في الدوائر الخارجية تعتمد على الدوائر الداخلية؛ لا يمكن للـ Domain Core أن يعرف أي شيء عن Express أو Prisma.

02

طبقة الكيانات (Domain Entities)

كائنات الأعمال الجوهرية الغنية بالقواعد والقيم (e.g. Money Value Object, User Entity) والخالية من أي مكتبات خارجية.

03

حالات الاستخدام (Application Use Cases)

أفعال النظام المحددة (مثل RegisterUserUseCase أو CheckoutCartUseCase) التي تنسق تدفق البيانات بين الكيانات والمنافذ.

04

المنافذ (Ports - Interfaces)

عقود برمجية واجهات (Interfaces) تحدد ما يحتاجه النطاق من العالم الخارجي (مثل IUserRepository, INotificationService).

05

المحولات (Adapters - Implementations)

الأكواد التقنية التي تطبق الواجهات وتتحدث مع العالم الخارجي (ExpressController, PrismaUserRepository, StripePaymentAdapter).

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

نفحص ملفات الـ Domain و Use Cases: يجب ألا تجد في رأس أي ملف أي جملة import تشير إلى مكتبات خارجية مثل express أو prisma أو mongoose أو axios! يجب أن تحتوي حصراً على أنواع JavaScript/TypeScript القياسية والـ Interfaces الخاصة بالنظام. إذا تمكنت من نسخ مجلد domain/use-cases بالكامل وتشغيله في تطبيق CLI أو في متصفح React دون أي خطأ استيراد، فالمعمارية نظيفة بنسبة 100%.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

// domain/use-cases/register-user.ts (Zero External Dependencies) // حالة استخدام نقية تماماً
export class RegisterUserUseCase {                   // فئة حالة الاستخدام
  constructor(                                       // حقن المنافذ
    private userRepo: IUserRepositoryPort, // Outbound Port // منفذ المستودع
    private hasher: IPasswordHasherPort // Outbound Port // منفذ التشفير
  ) {}                                               // نهاية البناء
  async execute(command: RegisterUserCommand): Promise<UserEntity> { // تنفيذ الأمر
    const hashedPassword = await this.hasher.hash(command.password); // تشفير عبر المنفذ
    const user = new UserEntity(command.email, hashedPassword); // Business Entity // إنشاء كيان النطاق
    return await this.userRepo.save(user);           // الحفظ عبر المنفذ
  }                                                  // نهاية التنفيذ
}                                                    // نهاية الكود

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ كارثي: استيراد Prisma أو Express داخل Use Case أو Entity
import { PrismaClient } from "@prisma/client"; // كسر قاعدة الاعتمادية وجعل النطاق عبداً للـ ORM!
✅ الحل الهندسي القياسي (Best Practice)
// الحل المعماري النظيف: الاعتماد على Port Interface مجردة
import { IUserRepositoryPort } from "../ports/user-repository.port"; // النطاق يحدد العقد فقط

التشخيص الهندسي: الاعتماد على المكتبات الخارجية داخل الـ Domain يربط كود الأعمال بالبنية التحتية، بينما استخدام الـ Ports يحافظ على استقلالية النظام.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: متى يكون تطبيق Clean Architecture قراراً هندسياً عبقرياً ومتى يكون Over-Engineering مهدراً للوقت والموارد؟

يكون قراراً عبقرياً وإلزامياً: في الأنظمة المؤسسية الكبرى (Enterprise Applications) ذات منطق الأعمال المعقد (Complex Domain Logic)، والمشاريع طويلة الأجل التي يعمل عليها عشرات المهندسين والتي تتطلب استقراراً بنكياً واختبارات معزولة 100%. ويكون Over-Engineering ضاراً: في تطبيقات الـ CRUD البسيطة، أو مشاريع الـ MVPs والاستارتابس في مراحل التحقق الأولى، حيث تضيف كثرة الطبقات والـ Mappers والـ Interfaces تعقيداً وبطئاً في سرعة التسليم (Time-to-Market) دون فائدة حقيقية تبررها.
