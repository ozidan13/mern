المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

أغلب مطوري الويب يبدأون مباشرة باستخدام Express.js أو NestJS، ولا يعرفون كيف يتحدث الخادم مع المتصفح تحت الغطاء! ماذا يحدث في الحقيقة عندما يرسل المتصفح طلب HTTP؟ المتصفح يفتح مقبس اتصال TCP Socket مع الخادم، ويرسل بايتات نصية مشفرة تبدأ بـ GET /api/users HTTP/1.1\r\nHost: api.codehub.dev\r\n\r\n. وحدة **node:http** في Node.js هي المسؤولة عن اعتراض هذه البايتات، وتمريرها لمحلل الـ HTTP (llhttp Parser)، وتغليفها في كائنين سحريين: - req: وهو عبارة عن تدفق قراءة (Readable Stream) يستقبل جسم الطلب على أجزاء. - res: وهو تدفق كتابة (Writable Stream) يرسل كود الحالة والرؤوس وجسم الرد للعميل. فهم هذه الطبقة المنخفضة هو الفارق الحقيقي عندما تحتاج لبناء بروكسي عكسي (Reverse Proxy)، أو التحكم في رؤوس الأمان (Security Headers)، أو بناء ترقية اتصالات حية **WebSockets** من الصفر.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

إنشاء الخادم الأصلي بـ http.createServer()

تسجيل دالة requestHandler تستقبل كائني (req, res) وتنفذ معالجة الطلبات بشكل لاتزامني فائق السرعة.

02

قراءة جسم الطلب عبر تدفقات Streams (req chunks)

تجميع بايتات البيانات القادمة بـ req.on("data") وتجميعها في Buffer عند اكتمال حدث req.on("end").

03

إرسال الردود ورؤوس الـ HTTP Headers

استخدام res.writeHead(200, { "Content-Type": "application/json" }) وكتابة المحتوى بـ res.end().

04

إدارة اتصالات Keep-Alive المستمرة

إعادة استخدام نفس اتصال الـ TCP لخدمة طلبات متعددة لنفس العميل لتفادي تكرار مصافحة الـ TCP Handshake.

05

ترقية الاتصال لـ WebSockets بحدث Upgrade

اعتراض حدث server.on("upgrade") والتحقق من صلاحية العميل ومصافحة الترقية لنقل المقبس لبروتوكول ثنائي الاتجاه.

تحدي التوقع قبل التشغيل · Predict Before You Run

🤔 سؤال تحدي كبار المهندسين:

ماذا يحدث إذا قمت باستدعاء res.write("data") بعد استدعاء res.end() في خادم Node.js؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

سيرمي المحرك خطأ فورياً من نوع Error [ERR_STREAM_WRITE_AFTER_END]: write after end. بمجرد استدعاء res.end()، يقوم Node.js بإنهاء تدفق الـ Writable Stream وإرسال حزمة الـ FIN في اتصال TCP وإغلاق القناة للعميل، ولا يُسمح بكتابة أي بيانات إضافية بعدها.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

import http from "node:http";                        // استيراد وحدة HTTP الأصلية
const server = http.createServer(async (req, res) => { // دالة استقبال الطلبات
  if (req.method === "POST" && req.url === "/api/echo") { // مطابقة المسار والطريقة
    const buffers = [];                              // مصفوفة تجميع البايتات
    for await (const chunk of req) {                 // قراءة الـ Stream بـ Async Iterator حديث
      buffers.push(chunk);                           // حفظ القطعة في الذاكرة
    }                                                // نهاية التدفق
    const data = Buffer.concat(buffers).toString();  // تحويل البايتات لنص
    res.writeHead(200, { "Content-Type": "application/json" }); // إرسال الرؤوس
    res.end(JSON.stringify({ received: data }));     // إرسال الرد وإغلاق التدفق
  }                                                  // نهاية الشرط
});                                                  // نهاية الخادم
server.listen(3000, () => console.log("Server listening on :3000")); // بدء الاستماع

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع: نسيان استدعاء res.end() في أحد مسارات الكود
app.get("/status", (req, res) => {
  if (isMaintenance) {
    res.write("Maintenance Mode"); // نسيان res.end() يعلق متصفح العميل في انتظار لانهائي حتى الـ Timeout!
  }
});
✅ الحل الهندسي القياسي (Best Practice)
// الحل الصحيح: ضمان إنهاء الرد دائماً
app.get("/status", (req, res) => {
  if (isMaintenance) {
    return res.end("Maintenance Mode"); // إنهاء صريح للاتصال
  }
  res.end("Operational");
});

التشخيص الهندسي: عدم إغلاق تدفق الاستجابة بـ res.end() يترك مقبس اتصال TCP مفتوحاً ومعلقاً لدى العميل حتى تنتهي مهلة الاتصال بعد 60-120 ثانية، مما يستهلك موارد الخادم.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف يعمل بروتوكول HTTP/2 و HTTP/3 في خوادم Node.js وما هي ميزة الـ Multiplexing التي قضت على مشكلة Head-of-Line Blocking؟

في HTTP/1.1، كل اتصال TCP يستطيع إرسال طلب واحد فقط في نفس الوقت (Serial). إذا تأخر طلب، تتعطل باقي الطلبات خلفه (Head-of-Line Blocking). في HTTP/2 (عبر وحدة node:http2)، يتم تقسيم الاتصال الواحد إلى Streams متوازية ثنائية (Binary Frames)، مما يتيح إرسال واستقبال مئات الطلبات والردود المتزامنة على اتصال TCP واحد دون أي انتظار (Multiplexing). وفي HTTP/3، تم استبدال TCP ببروتوكول QUIC القائم على UDP للقضاء على Head-of-Line Blocking على مستوى طبقة النقل (Transport Layer) أيضاً عند فقدان حزم البيانات في الشبكات اللاسلكية.
