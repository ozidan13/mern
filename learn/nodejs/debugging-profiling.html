Node.js Production Debugging: Chrome DevTools Inspector, Memory Leaks & CPU Profiling

تشخيص وتصحيح خوادم Node.js: الربط مع Chrome DevTools، كشف تسريبات الذاكرة والـ CPU Profiling

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • ربط خادم Node.js المباشر بـ Chrome DevTools عبر خيار --inspect لتصحيح الكود بالـ Breakpoints.
  • أخذ لقطات الذاكرة (Heap Snapshots) والمقارنة بينها لكشف تسريبات الذاكرة (Memory Leaks).
  • تسجيل ملفات أداء المعالج (CPU Profiles) ومخططات اللهب (Flamegraphs) لتحديد الدوال البطيئة.
  • تشخيص تعليق الـ Event Loop باستخدام وحدة node:perf_hooks ومقاييس ELD (Event Loop Delay).

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في بيئة التطوير، عندما يحدث خطأ، يضع المطور console.log() في كل مكان. لكن في بيئة الإنتاج عندما يبدأ الخادم باستهلاك 100% من الـ CPU فجأة، أو عندما يرتفع استهلاك الـ RAM من 200MB إلى 4GB حتى ينهار الخادم بـ Out of Memory (OOM Crash) كل 3 ساعات... الـ console.log لن يفيدك بشيء! أنت بحاجة لأدوات جراحية دقيقة لفحص ما بداخل محرك V8 أثناء عمل الخادم الحقيقي. يوفر Node.js بروتوكول فحص متقدم **V8 Inspector Protocol**: - يمكنك تشغيل الخادم بـ node --inspect والاتصال به من متصفح كروم وتفعيل الـ Breakpoints الحية. - يمكنك تسجيل **CPU Profile** وتوليد **Flame Graph** يوضح بالمللي ثانية أين يقضي المعالج وقته. - يمكنك أخذ **Heap Snapshots** ومقارنتها عبر الزمن لمعرفة أي كائنات ومصفوفات يتم حبسها في الذاكرة وتتسبب في تسريب الـ RAM. في هذا الدرس الختامي لمسار Node.js 24، هنتعلم إزاي ننقذ الخوادم المنهارة في بيئات الإنتاج ونشخص أسباب بطء المعالج واختناق الذاكرة.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

تفعيل بروتوكول الفحص المباشر (node --inspect)

تشغيل الخادم مع فتح منفذ WebSocket مخصص (افتراضياً 9229) للاتصال بـ Chrome DevTools عبر chrome://inspect.

02

أخذ لقطات الذاكرة (Heap Snapshot Analysis)

تسجيل لقطتين للذاكرة والمقارنة بينهما (Comparison View) لتحديد الكائنات التي زاد عددها ولم تُحذف بـ Garbage Collector.

03

مخططات اللهب وتحليل المعالج (CPU Flamegraphs)

تسجيل CPU Profile لتوليد مخطط بصري يوضح تسلسل استدعاءات الدوال، حيث تمثل الدوال العريضة عنق الزجاجة (Bottlenecks).

04

قياس تأخير الـ Event Loop بـ perf_hooks

استخدام monitorEventLoopDelay() لقياس زمن تأخر الخيط الرئيسي بالنانوثانية عند معالجة المهام الثقيلة.

05

التشخيص بدون إيقاف الخادم (Production Diagnostic Reports)

توليد تقارير JSON تشخيصية فورية بـ process.report.writeReport() تحتوي على تفاصيل الـ Heap والـ OS Threads.

تحدي التوقع قبل التشغيل · Predict Before You Run

🤔 سؤال تحدي كبار المهندسين:

ما هو الفرق بين Retained Size و Shallow Size عند تحليل كائنات لقطة الذاكرة (Heap Snapshot) في Chrome DevTools؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

الـ Shallow Size هو حجم الذاكرة التي يحجزها الكائن نفسه فقط في الـ Heap (مثل بنية الكائن ومؤشراته). أما الـ Retained Size فهو الحجم الإجمالي للذاكرة التي ستتحرر تلقائياً إذا تم حذف هذا الكائن مع جميع الكائنات الفرعية التابعة له والتي لا يمكن الوصول إليها إلا من خلاله (Dominator Tree). عند البحث عن تسريبات الذاكرة، يتم الفرز دائماً حسب Retained Size.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

import { monitorEventLoopDelay } from "node:perf_hooks"; // استيراد وحدة مقاييس الأداء
export const eldHistogram = monitorEventLoopDelay({ resolution: 10 }); // إنشاء مدرج تكراري دقيق للـ Event Loop
eldHistogram.enable();                               // بدء التسجيل الفعلي
export function getEventLoopHealth() {               // دالة فحص صحة الخادم
  const p99LatencyMs = eldHistogram.percentile(99) / 1e6; // حساب زمن التأخير للنسبة 99%
  return {                                           // إرجاع التقرير
    healthy: p99LatencyMs < 50, // صحي إذا كان التأخير أقل من 50ms // معيار الصحة
    p99DelayMs: p99LatencyMs.toFixed(2)              // قيمة التأخير
  };                                                 // نهاية التقرير
}                                                    // نهاية الدالة

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تشخص مشكلة Memory Leak حية في خادم إنتاج داخل Kubernetes Cluster دون التسبب في إيقاف الخدمة أو إعادة تشغيل الـ Pod؟

1. نستخدم أمر kubectl port-forward pod-name 9229:9229 لإنشاء نفق آمن لمنفذ الفحص المفتوح على localhost داخل الـ Pod. 2. نفتح Chrome DevTools عبر chrome://inspect للاتصال بالخادم. 3. نأخذ Heap Snapshot أولي. 4. نرسل دفعة طلبات اختبارية ثم نأخذ Snapshot ثانٍ. 5. ننتقل إلى Comparison View ونفرز بـ # Delta و Retained Size للبحث عن كائنات (مثل Closures أو Timers أو Arrays) التي زاد عددها ولم تُحرر، مما يكشف السطر المسبب للتسريب بدقة بيكسلية بدون التأثير على مستخدمي الموقع.
