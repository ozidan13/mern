Event-Driven Architecture: EventEmitter, Custom Events & Memory Leak Detection

المعمارية الموجهة بالأحداث: EventEmitter، الأحداث المخصصة وكشف تسريبات الذاكرة

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • فهم صلب المعمارية الموجهة بالأحداث في Node.js وكيف تُبنى عليه وحدات http و streams و sockets.
  • إنشاء فئات مخصصة ترث من EventEmitter لإرسال واستقبال الأحداث المخصصة (Custom Domain Events).
  • كشف وتشخيص تحذيرات تسريب الذاكرة الشهيرة (MaxListenersExceededWarning).
  • استخدام events.once() للانتظار اللاتزامني النظيف للأحداث عبر async/await.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

كل شيء في Node.js مبني على نمط الملاحظ (Observer Pattern) عبر صنف EventEmitter: خادم الـ HTTP يطلق حدث 'request'، والـ Socket يطلق حدث 'data'، وتدفق الملفات يطلق حدث 'end'. لكن في المشاريع الإنتاجية، يقع المطورون في واحدة من أشهر مشاكل الذاكرة في Node.js: 

(node:4120) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 request listeners added.
هذا التحذير لا يظهر عبثاً! إذا قمت بتسجيل مستمع أحداث emitter.on('event', callback) داخل كل طلب HTTP يطلبه العميل دون حذفه عند انتهاء الطلب، فإن كائن الـ EventEmitter سيحتفظ بمراجع لكل دوال الـ Callbacks في الذاكرة للأبد، مما يمنع مجمع القمامة (Garbage Collector) من تحريرها، حتى ينفد رصيد الـ RAM وينهار الخادم! في هذا الدرس، هنتعلم إزاي نبني Event-Driven Micro-Architecture نظيفة، إزاي نستخدم events.once() مع الـ Promises، وإزاي ننظف المستمعين تلقائياً عبر AbortSignal.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

تسجيل وإطلاق الأحداث (emit & on)

استخدام emitter.on() لتسجيل المستمع و emitter.emit() لإطلاق الحدث مع تمرير البيانات لكافة المشتركين بشكل تزامني.

02

الاستماع لمرة واحدة فقط بـ once()

تسجيل دالة تُنفذ لمرة واحدة فقط ثم تقوم بإلغاء تسجيل نفسها تلقائياً من الذاكرة بمجرد وقوع الحدث.

03

حدود المستمعين وكشف تسريب الذاكرة

الحد الافتراضي هو 10 مستمعين لكل حدث؛ تجاوزه يطلق تحذيراً فورياً لتنبيهك بوجود تسريب في الدوال المسجلة.

04

الانتظار اللاتزامني للأحداث عبر events.once()

تحويل أي حدث إلى Promise باستخدام await events.once(server, "listening") لدمج نمط الأحداث مع async/await.

05

إلغاء الاشتراكات عبر AbortSignal

تمرير { signal: abortController.signal } في emitter.on() في Node 24 لحذف المستمع تلقائياً عند إلغاء العملية.

🤔 سؤال تحدي كبار المهندسين:

ماذا يحدث إذا تم إطلاق حدث من نوع "error" على كائن EventEmitter ولم يكن هناك أي مستمع مسجل له emitter.on("error")؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

إذا أطلق EventEmitter حدث "error" دون وجود مستمع واحد على الأقل، سيعاملها Node.js كاستثناء غير معالج (Unhandled Exception)، وسيقوم فوراً بطباعة الـ Stack Trace وإنهاء عملية الخادم بالكامل process.exit(1)! لذلك يجب دائماً تسجيل مستمع لأحداث الخطأ على كل EventEmitter.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

import { EventEmitter, once } from "node:events";    // استيراد وحدة الأحداث الرسمية
class UserNotifier extends EventEmitter {            // فئة ترث من EventEmitter
  sendWelcome(user) {                                // دالة تنشيط الحدث
    this.emit("user:registered", user);              // إطلاق الحدث مع كائن المستخدم
  }                                                  // نهاية الميثود
}                                                    // نهاية الفئة
const notifier = new UserNotifier();                 // إنشاء النسخة
notifier.on("user:registered", (u) => analytics.track(u.id)); // تسجيل مستمع التحليلات

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ شائع مسبب لتسريب الذاكرة: إضافة المستمع داخل مسار الطلبات دون حذفه
app.get("/events", (req, res) => {
  eventBus.on("update", (data) => res.write(data)); // كل طلب يضيف مستمعاً جديداً في الذاكرة للأبد!
});
✅ الحل الهندسي القياسي (Best Practice)
// الحل الهندسي: حذف المستمع عند إغلاق العميل للاتصال
app.get("/events", (req, res) => {
  const handler = (data) => res.write(data);
  eventBus.on("update", handler);
  req.on("close", () => eventBus.off("update", handler)); // تنظيف الذاكرة فوراً
});

التشخيص الهندسي: عدم إزالة دوال الـ Callbacks عند انتهاء حاجة العميل إليها يبقي مراجعها حية في الذاكرة ويؤدي إلى انهيار الخادم بـ Memory Leak بعد آلاف الطلبات.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: كيف تحل مشكلة انتشار الأحداث في معمارية المايكروسيرفس الموزعة (Distributed Microservices) باستخدام Redis Pub/Sub؟

الـ EventEmitter العادي يعمل داخل عملية Node.js واحدة على سيرفر واحد فقط. عندما نوزع التطبيق على 10 خوادم أو كونتيرات Docker، نربط الـ EventEmitters بمحرك رسائل مركزي مثل Redis Pub/Sub أو RabbitMQ: عندما يقع حدث في السيرفر 1، يرسل رسالة Redis PUBLISH channel payload، وتقوم باقي الخوادم التسعة المشتركة SUBSCRIBE باستقبال الرسالة وإطلاق EventEmitter محلي لمعالجة الحدث، محققين تزامناً موزعاً فائق السرعة.
