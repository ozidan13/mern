File System (fs/promises): Async I/O, Streams & Safe Atomic File Writes

نظام الملفات fs/promises: عمليات الإدخال والإخراج اللاتزامنية والكتابة الذرية الآمنة (Atomic Writes)

🎯 الأهداف الهندسية لهذا الدرس (Learning Objectives)

  • التمييز الصارم بين دوال fs المتزامنة (Sync: تحظر الـ Event Loop) واللاتزامنية (fs/promises).
  • تطبيق مبدأ الكتابة الذرية للملفات (Atomic File Writes) لمنع تلف البيانات وتفريغ الملفات عند انقطاع الكهرباء.
  • إدارة أذونات الملفات (File Permissions & POSIX Modes) والمجلدات التكرارية recursive mkdir.
  • استخدام FileHandle لإدارة تدفقات الملفات الكبيرة وإغلاق الموارد بأمان.

المشكلة الهندسية والسياق الواقعي · The Architectural Problem

رؤية الواقع العملي والنموذج الذهني · Real-World Context & Mental Model

في خادم Node.js يستقبل 2000 طلب في الثانية، تخيل أن هناك مطوراً كتب داخل مسار تسجيل المستخدمين: fs.writeFileSync('users.json', JSON.stringify(users))! ماذا يحدث للسيرفر في هذه اللحظة؟ دالة writeFileSync تحظر خيط التنفيذ الرئيسي بالكامل (Blocking the Event Loop) حتى ينتهي القرص الصلب الميكانيكي أو الـ SSD من كتابة الملف. خلال هذه الميلي ثواني، لن يستطيع السيرفر الرد على أي مستخدم آخر، وسترتفع مؤشرات الـ Latency إلى السماء! الكارثة الأكبر هي تلف الملفات (Data Corruption): لو انقطع التيار الكهربائي أو توقف الخادم في منتصف عملية الكتابة، سيتحول الملف إلى ملف تالف بحجم 0 بايت وتفقد كل بيانات المستخدمين للأبد! الحل المعماري هو الانتقال الكامل إلى **fs/promises** واستخدام تقنية **الكتابة الذرية (Atomic File Writes)** عبر كتابة ملف مؤقت ثم استبداله بـ fs.rename() في عملية POSIX ذرية لا تقبل التجزئة.

كيف تعمل المنظومة خطوة بخطوة · Mechanics & Execution Pipeline

01

التفويض لمكتبة libuv Thread Pool

عمليات fs/promises لا تحظر الـ Event Loop؛ بل تفوض العمليات الثقيلة لـ 4 خيوط عمل داخلية في libuv.

02

إنشاء المجلدات التكرارية الآمنة (mkdir with recursive)

استخدام await fs.mkdir(dirPath, { recursive: true }) لإنشاء شجرة المجلدات المتداخلة دون الحاجة لفحص وجودها مسبقاً.

03

استراتيجية الكتابة الذرية (Atomic Write Pattern)

كتابة البيانات في ملف مؤقت .tmp.json ثم استخدام await fs.rename() لاستبدال الملف الأصلي فورياً في عملية ذرية مدعومة بنظام التشغيل.

04

إدارة مؤشرات الملفات عبر FileHandle

فتح الملف بـ fs.open() والحصول على FileHandle للقراءة أو الكتابة المجزأة، مع ضمان إغلاقه دائماً بـ handle.close() داخل كتلة finally.

05

مراقبة تغييرات الملفات (File Watchers)

استخدام fs.watch() مع معالجة أحداث التعديل والحذف لمراقبة ملفات الإعدادات وتحديثها في الذاكرة تلقائياً.

🤔 سؤال تحدي كبار المهندسين:

لماذا يعتبر فحص وجود الملف بـ fs.access() قبل محاولة قراءته بـ fs.readFile() نمطاً سيئاً (Race Condition Anti-Pattern)؟

اضغط هنا للكشف عن الإجابة والتحليل الهندسي الدقيق

هذا ما يعرف هندسياً بـ Time-of-Check to Time-of-Use (TOCTOU Race Condition). بين لحظة فحص وجود الملف بـ fs.access ولحظة استدعاء fs.readFile، قد تقوم عملية أخرى في نظام التشغيل بحذف الملف أو تعديل أذوناته! الحل السليم هو محاولة قراءة الملف مباشرة والتقاط خطأ ENOENT داخل كتلة try/catch.

تشريح الكود المعماري سطراً بسطر · Annotated Code Anatomy

import fs from "node:fs/promises";                   // استيراد واجهة الوعود اللاتزامنية الأصلية
import path from "node:path";                        // وحدة معالجة المسارات
export async function saveConfigAtomically(filePath, data) { // دالة الكتابة الذرية
  const dir = path.dirname(filePath);                // استخراج مسار المجلد
  await fs.mkdir(dir, { recursive: true });          // ضمان وجود المجلدات المتداخلة
  const tempFile = `${filePath}.tmp.${Date.now()}`;  // مسار الملف المؤقت
  await fs.writeFile(tempFile, JSON.stringify(data, null, 2), "utf-8"); // كتابة البيانات في الملف المؤقت
  await fs.rename(tempFile, filePath);               // استبدال ذري POSIX مضمون بنسبة 100%
}                                                    // نهاية الدالة

معرض الأخطاء الشائعة والحلول الهندسية · Production Mistakes Gallery

❌ الكود المسبب للأعطال (Anti-Pattern)
// خطأ كارثي في خوادم الإنتاج: استخدام الدوال المتزامنة في المسارات
app.get("/data", (req, res) => {
  const file = fs.readFileSync("./large-database.json"); // يوقف السيرفر بالكامل عن استقبال اتصالات جديدة!
  res.send(file);
});
✅ الحل الهندسي القياسي (Best Practice)
// الحل الهندسي: استخدام fs/promises اللاتزامني بالكامل
app.get("/data", async (req, res) => {
  const file = await fs.readFile("./large-database.json", "utf-8"); // غير حاجب للـ Event Loop
  res.send(file);
});

التشخيص الهندسي: استخدام readFileSync أو writeFileSync يحظر الخيط الرئيسي في Node.js ويشل قدرة الخادم على معالجة الطلبات المتزامنة الأخرى، مما يرفع زمن الـ Response Time لثوانٍ معدودة.

💼 سؤال إنترفيو للمهندسين الكبار (Senior Interview Question)

سؤال إنترفيو للمهندسين الكبار: ما هو الفرق بين قراءة ملف بحجم 2GB بـ fs.readFile وبين قراءته عبر fs.createReadStream وماذا يحدث للـ RAM في الحالتين؟

دالة fs.readFile تحاول تحميل محتوى الملف بالكامل (2GB) دفعة واحدة داخل ذاكرة الـ RAM المخصصة لـ V8 Heap Memory، مما يؤدي لتجاوز حد الذاكرة الافتراضي (Old Space Limit) وانهيار الخادم فوراً بخطأ JavaScript heap out of memory! أما fs.createReadStream فتقوم بقراءة الملف على أجزاء صغيرة (Chunks بحجم 64KB افتراضياً)، وتمريرها في خط أنابيب (Pipeline) دون أن يتجاوز استهلاك الذاكرة أكثر من بضعة ميجابايتات مهما كان حجم الملف ضخماً.
